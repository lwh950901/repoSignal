# 月度公开研究稿 Markdown 合同

本目录只存放会被网站发现的冻结月报，文件名必须是 `YYYY-MM.md`。外部事实必须在发布前完成研究并固化；构建过程不得联网。完整证据和失败记录放在相邻的 `monthly-research/`，该目录不参与站点发现。

公开月报按以下顺序书写：

1. 一级标题：`RepoSignal 月度精选｜YYYY-MM`。
2. 引用元数据：数据截止、研究范围、深度候选数、验证说明。
3. `本月结论`：一句编辑结论，不写未经核实的市场规模或收益率。
4. `Top 5 仓库`：恰好五项，按总分降序；每项包含定位、本月变化、事实指标、能力与限制、验证等级、六维评分、反对理由、判断和来源。
5. `真实业务与项目机会`：零至三项；每项必须完整包含摘要、真实问题、市场与现有方案、产品定义、仓库组合、组合链路、自行开发部分、MVP、业务判断和证据边界。
6. `研究说明`：解释候选池、评分模型、验证等级、事实与推断的边界。

固定枚举：

- 验证等级只表示实际核实深度，不表示项目质量排名：`L0` 为资料核实，`L1` 为成功安装或启动，`L2` 为单仓库核心流程跑通，`L3` 为至少两个仓库完成真实数据连接，`L4` 为在授权的真实任务中验证。公开月报必须在首次出现等级缩写前解释这组含义。
- 需求状态：`已确认需求`、`有需求信号`。
- 组合结论：`已验证可行`、`文档层面可行`、`部分可行`、`暂不可行`。
- 业务判断：`值得进入用户验证`、`值得做技术实验`、`继续观察`、`暂不建议`。
- 形态：`商业产品`、`企业内部工具`、`新开源项目`。

六维评分的上限依次为：本月重要性 20、实际价值 25、工程质量 20、差异化 15、维护可持续性 10、采用证据 10；总分必须等于六项之和且位于 0–100。仓库链接必须是与显示名称一致的 GitHub canonical `owner/repo`，同一公开月报不得重复仓库身份。

业务方案发布门槛：两类独立需求证据；至少一个商业产品、一个开源/自托管方案和一个现实流程；2–5 个不重叠职责的仓库；全部核心仓库达到 L0，至少一个达到 L2；明确连接方式、自研缺口、MVP 成功指标、停止条件、来源和核实日期。不满足时不发布占位方案。
