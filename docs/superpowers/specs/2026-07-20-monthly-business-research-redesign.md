# RepoSignal 月度精选：业务研究与项目组合重构设计

## 1. 变更说明

本设计重构月度精选的内容与研究方法，替代原设计中的“场景选型、分类推荐、本月观察信号和角色行动建议”。原有月、周、日导航、静态路由、历史归档、本地搜索和无 JavaScript 降级继续保留。

本设计与 `2026-07-20-monthly-selection-design.md` 冲突时，以本设计为准。

现有 `2026-07` 月报是用于跑通 UI 的编辑示例，不具备正式业务研究所需的需求、竞品和项目组合证据。新版发布前必须重新研究和撰写，不能将现有文案继续标记为正式结论。

## 2. 页面回答的问题

月报只回答三类彼此独立的问题：

1. **Top 5：**本月哪五个单独的 GitHub 仓库最值得投入时间关注？
2. **业务研究：**本月仓库反映出哪些真实存在、值得验证的业务或项目机会？
3. **项目组合：**哪些 GitHub 仓库能够帮助实现这些机会，组合到什么程度，仍缺什么？

Top 5 与业务研究互不约束。Top 5 项目不必进入业务组合，业务组合成员也不必进入 Top 5。两部分可以共享核实后的仓库事实，但不得共享排名或结论。

## 3. 非目标

- 不按“独立开发者、技术负责人、AI 产品创业者”分组推荐。
- 不为了保持栏目数量而生成业务想法、趋势或行动建议。
- 不把方向相似、技术栈相同或都带有 Agent 标签的仓库视为可组合。
- 不使用没有来源的市场规模、收入、客户数量或效率提升比例。
- 不把 README 声明、Stars 或 AI 推断当作真实需求证明。
- 不要求每月固定发布业务方案；没有方案通过验证时允许为零。
- 不在构建阶段访问外部服务；研究结果先固化为本地 Markdown，再由 Astro 静态构建。

## 4. 最终信息架构

公开月报保持一个长页面，顺序固定为：

1. **月度封面**：月份、数据截止日期、研究范围和一句编辑结论。
2. **Top 5 仓库**：独立单仓库排名、评分证据和反对理由。
3. **真实业务与项目机会**：0–3 个通过发布门槛的深度方案。
4. **研究说明**：来源、核实日期、验证深度和仍属推断的边界。

“能力地图”只允许作为内部发现业务假设的研究材料，不在公开页面展示。“暂不建议方向”不是固定栏目；只有研究产生明确否定结论且对读者有帮助时，才附在对应业务方案中。

## 5. Top 5 排名

### 5.1 入围门槛

仓库必须真实可访问、未归档、许可证明确、用途与安装入口清楚，并在当月存在可核实的首次发现、正式发布、关键能力变化、重要修复或采用信号。只依赖历史影响力、README 小改动、营销热度或可疑增长的项目不能入围。

### 5.2 深度候选

系统先使用候选账本、日报和周报形成当月候选池，再筛出约 15 个深度候选。深度候选应在月末重新核实 GitHub 仓库、官方文档、许可证、release、近期有效提交、issue/PR、安装方式和采用证据，不能直接复制日报中的旧指标。

### 5.3 评分模型

Top 5 使用统一的 100 分编辑评分：

| 维度 | 分值 | 判断内容 |
|---|---:|---|
| 本月重要性 | 20 | 为什么必须在本月关注 |
| 实际价值 | 25 | 是否解决明确且可验证的问题 |
| 工程质量 | 20 | 安装、测试、文档、发布和安全材料 |
| 差异化 | 15 | 与替代项目相比的真实区别 |
| 维护可持续性 | 10 | 维护节奏、响应和关键人员风险 |
| 采用证据 | 10 | 客户案例、下游集成、真实讨论和使用 |

Stars 和 Forks 只能作为采用证据的辅助信号，不能单独决定排名。第一期应先对深度候选试评分并校准一次权重，公开说明这是可解释的编辑评分，不是绝对客观排名。

默认按总分排序。只有数据质量差异、安全或许可证风险、无法用分数表达的重大限制，以及非常接近的同分情况允许人工调整；调整必须保存理由，不能为了覆盖不同技术方向而改榜。

### 5.4 Top 5 展示字段

每个项目展示：

- 排名、仓库和一句准确定位；
- 本月具体变化及来源；
- Stars、Forks、release、最近有效提交、许可证和核实日期；
- 核心能力、工程成熟度和明确限制；
- 安装或运行验证等级；
- 六项评分和总分；
- “为什么它可能不应入选”的主要反对理由；
- 最终入选判断。

不再展示主要角色、次要角色和泛化的“最佳使用场景”。

## 6. 业务研究

### 6.1 数量与形态

每月发布 0–3 个经过核实的业务或项目机会，不为证据充分的月份扩大上限。允许的主要形态为：

- 商业产品；
- 企业内部工具；
- 新开源项目。

每个方案只能选择一种主要形态。内部工具不强行编写收费模式，开源项目不包装成已经成立的商业市场。

### 6.2 仓库月份范围

每个方案至少有一个触发业务判断的核心仓库来自本月候选。允许加入历史月份或外部发现的成熟辅助仓库，但必须明确标记“本月核心仓库”和“补充组件”，并执行相同的仓库、许可证和维护核实。

该规则避免为了只使用本月项目而构造残缺方案，同时保证业务研究仍由本月开源信号触发。

### 6.3 业务发现漏斗

研究人员先从当月仓库的新增能力、上下游缺口、现有商业产品缺口和高成本人工流程中形成 5–10 个内部假设。随后调查真实需求与现有方案，只保留 2–5 个候选业务，再进行仓库组合验证，最终发布 0–3 个。

内部假设不进入公开页面，未通过的方案也不自动形成“本月不建议做什么”。

### 6.4 真实需求证据

每个正式方案至少需要两类相互独立的需求证据，并标记强度。

强证据包括商业产品真实收费、官方客户案例、企业公开采用、采购或服务需求、可核实的付费行为，以及多个团队独立建设相似内部系统。中等证据包括反复出现的 GitHub issue、社区问题、公开内部方案和持续增加的第三方集成。Stars、单篇趋势文章、项目作者的市场声明和 AI 推断属于弱证据，不能单独支持正式方案。

需求状态只允许：

- **已确认需求**：至少有一项强证据；
- **有需求信号**：存在多项独立中等证据，但尚无付费证明；
- **推测需求**：主要依赖弱证据，不得进入正式业务正文。

### 6.5 市场与替代方案

每个方案调查 3–5 个代表性替代方案，至少包括一个商业产品、一个开源或可自托管方案，以及一个人工或企业内部流程。记录其服务对象、核心能力、公开价格、部署方式、采用证据、限制与本方案差异。

没有公开价格、收入、客户数量或市场规模时必须写“未知”，禁止估算或补写。只有真实问题、现有方案缺口、缺口的重要性和开源组合的可行性同时成立，才能判断存在值得验证的机会。

### 6.6 默认市场范围

第一版默认研究全球开发者工具和企业软件市场。若方向明显依赖中国市场的私有部署、本地模型或合规需求，可增加“中国市场适配”说明，但不同时覆盖所有地区和所有客户。每个方案只定义一个首要目标市场和目标用户。

## 7. GitHub 仓库组合验证

### 7.1 组合规则

一个方案使用 2–5 个核心仓库。每个仓库必须承担核心引擎、数据/检索、工作流编排、用户交互、运行/评测等明确且不重复的职责。

允许的关系包括：A 的输出可成为 B 的输入、A 与 B 覆盖工作流的不同阶段、官方接口可以连接，或适配层规模明确且合理。功能相同的竞品、只有主题相似的项目、只能人工复制数据连接的项目，以及需要重写大部分代码的项目不得描述为组合。

### 7.2 核实字段

每个核心仓库至少核实：

- 官方仓库、许可证、归档状态、最近有效提交和 release；
- 真实用途、安装方式、主要技术栈和部署依赖；
- SDK、API、CLI 或其他集成入口；
- 输入、输出、认证、存储和外部服务依赖；
- 与组合中其他项目的功能重叠；
- 商用、数据安全和维护风险。

### 7.3 验证等级

| 等级 | 含义 |
|---|---|
| L0 信息核实 | 仓库、许可证、维护状态和文档已检查 |
| L1 安装验证 | 能安装并启动最小命令 |
| L2 核心流程 | 官方最小示例产生预期输出 |
| L3 组合实验 | 两个或多个仓库完成最小数据连接 |
| L4 真实任务 | 使用真实数据完成一项业务任务 |

所有核心仓库必须达到 L0；至少一个核心仓库达到 L2。组合优先达到 L3；未达到 L3 时必须标为“文档层面可行”或“部分可行”，不得声称已经验证组合成功。

### 7.4 可行性结论

组合结论只允许：

- **已验证可行**：核心流程和关键数据连接已经运行；
- **文档层面可行**：官方接口支持，尚未完成连接实验；
- **部分可行**：存在明确适配器、权限、存储或产品层缺口；
- **暂不可行**：接口、许可证、维护或实现成本形成关键阻碍。

每个方案必须列出可直接复用的能力、必须自行开发的部分、没有完成的验证和停止条件。

## 8. 单个业务方案的公开结构

每个方案固定包含：

1. **摘要卡**：名称、形态、目标用户、需求状态、竞品数量、组合仓库数量、最高验证等级、组合结论、商业判断和核实日期。
2. **真实问题**：用户、发生场景、当前流程、成本或风险，以及需求证据。
3. **市场与现有方案**：商业竞品、开源替代、人工流程和未满足需求。
4. **产品定义**：具体产品形态、核心工作流、第一版价值和明确非目标。
5. **仓库组合**：本月核心仓库与补充组件、各自职责、接入方式和验证等级。
6. **组合链路**：从用户输入、各仓库处理到最终输出的真实数据流。
7. **自行开发部分**：认证、适配器、存储、界面、审计或其他开源项目没有解决的能力。
8. **MVP 验证**：单一目标用户、输入、核心流程、输出、成功指标、停止条件和第一版不做的内容。
9. **业务判断**：谁可能付费或受益、价值实现方式、采用阻力、差异化和最终结论。
10. **证据边界**：已证实事实、推断、未验证内容、来源与核实日期。

商业判断只允许“值得进入用户验证、值得做技术实验、继续观察、暂不建议”。第一版不发布未经验证的收入预测、TAM 或效率提升百分比。

## 9. 发布门槛

业务方案只有满足以下条件才能进入公开月报：

- 至少达到“有需求信号”；
- 至少包含两类独立需求证据；
- 调查至少一个商业产品、一个开源/自托管替代和一个现实流程；
- 所有核心仓库完成 L0 核实，至少一个达到 L2；
- 说明仓库之间的连接方式、输入和输出；
- 明确列出自行开发部分；
- 给出可执行的 MVP、成功指标和停止条件；
- 外部事实附来源和核实日期；
- 推断没有被写成事实。

任一关键条件不满足时不发布。一个月没有业务方案通过门槛时，页面明确说明本月未发现通过完整验证的新机会，不生成占位内容。

## 10. 研究文件与公开页面

公开月报只展示结论、关键证据、评分和来源链接。完整研究材料保存在独立 Markdown 文件中，包括深度候选评分表、竞品调查、仓库核实、安装/组合实验摘要和失败记录。原始命令日志、大量重复指标和不影响结论的 issue 不进入公开页面。

建议目录：

```text
data/github-project-digest/monthly/YYYY-MM.md
data/github-project-digest/monthly-research/YYYY-MM/
  top5-scorecard.md
  business-<slug>.md
  repository-verification.md
```

`monthly/` 参与网站构建；`monthly-research/` 只作为编辑证据，不参与构建或搜索索引。第一版公开页面直接链接外部事实来源，不链接内部研究目录；以后若要公开研究摘要，需要另行设计公开路由。研究文件不得包含凭据、私有数据或不安全的运行日志。

## 11. 月报数据模型调整

新版 Markdown 和解析模型删除：

- 主要角色、次要角色；
- 分类推荐；
- 最佳使用场景；
- 固定观察信号；
- 按角色划分的行动建议。

新增：

- Top 5 的月度变化、事实指标、验证等级、六项评分、反对理由和来源；
- 0–3 个业务方案及其需求状态、市场证据、项目组合、验证等级、MVP、商业判断和证据边界；
- 研究范围和核实说明。

解析器继续严格校验发布必填项。Top 5 必须恰好五个；业务方案允许为零。链接、月份、日期、评分范围、验证等级和结论枚举错误时构建失败。外部网络只用于生成发布内容前的研究，不得影响已冻结月报的重复构建。

## 12. 第一版试运行范围

第一版只重做 `2026-07`：

1. 使用本地候选池筛选约 15 个 Top 5 深度候选；
2. 重新从官方 GitHub 与官方文档核实候选；
3. 试评分并校准一次权重，确定独立 Top 5；
4. 从当月仓库形成业务假设，但最多深入研究 3 个；
5. 最终只发布通过门槛的 0–3 个方案；
6. 至少对每个发布方案的一个核心仓库完成 L2；
7. 尽可能完成一个 L3 最小组合实验；无法完成时明确降级；
8. 保存评分、竞品、仓库和实验研究 Markdown；
9. 替换当前示例月报，并适配页面与解析器；
10. 复查桌面和移动端阅读层级、来源链接与无 JavaScript 导航。

第一版的成功标准不是凑出丰富内容，而是读者能够区分事实、推断和实际验证，并能据此决定是否继续研究某个仓库或业务方向。

## 13. 仍需在试运行中校准

- Top 5 六项权重是否导致成熟项目或大公司项目长期占优；
- 业务需求的两类证据门槛是否足够；
- L2/L3 验证在 API Key、GPU 和复杂部署条件下的实际成本；
- 公开页面与内部研究文件之间最合适的细节比例；
- 每月可持续完成的业务方案数量。

这些项目必须通过第一期真实研究校准，不提前包装成已验证规则。任何调整都应记录在研究文件和后续设计更新中。
