# 可行性方案探索池扩展设计

## 问题

当前可行性分析名义上有 11 个成熟方向模板，但候选高度集中在企业私有 RAG、
智能体交付和本地工作台；探索方向又要求至少 3 个可执行项目全部来自今日日报。
当今日日报中的项目能力面不足、项目属于资源索引，或项目之间无法形成数据流时，
探索候选直接归零，成熟候选则容易因相同方向冷却而归零。

此外，日报解析器没有识别 `可复用型` 小节，可能把前一个项目的字段覆盖为
`可复用型` 项目的字段，造成今日锚点丢失或身份错配。

## 目标

- 保留“少而可信、允许 0 个方案”的原则，不为凑数降低技术、证据或冷却门槛。
- 让每个可执行的今日项目都有机会成为探索种子。
- 允许从最近 90 天项目池补齐今日项目缺少的能力面。
- 防止历史高分项目取代今日项目，或长期成为固定配件。
- 修复 `可复用型` 日报小节的解析。

## 方案比较

### 方案 A：继续增加固定模板

实现简单，但只能增加名义方向；同一批高分项目仍会反复命中模板，不能解决探索候选
对今日日报结构的依赖。放弃。

### 方案 B：只修复日报解析

能恢复被漏掉的项目，但只要当天项目仍不足 3 个或数据流不连通，探索候选依旧为零。
作为必要修复纳入，但不足以单独解决问题。

### 方案 C：今日锚点加 90 天互补组件

以每个今日可执行项目为种子，从最近 90 天池内选择 2–4 个可连接、能力面不重复的
互补组件。保留既有闭环、证据、评分、冷却和数量上限。采用此方案。

## 组合规则

1. 今日锚点必须是可执行项目；Awesome List、资源索引、教程和纯内容仓库不能成为
   锚点或互补组件。
2. 每个探索候选恰好从一个今日锚点开始，最终包含 3–5 个组件，且今日锚点必须保留
   在主数据流中。
3. 互补组件先在今日日报中选择，不足时再从最近 90 天池补齐；只选择能通过现有
   能力输入输出连接规则的项目。
4. 同一能力面只保留一个组件。候选选择顺序综合考虑：能否连接、是否来自今日、
   近期复用次数、项目质量与稳定排序键。近期被反复采用的历史组件降权，但不直接
   禁用，以免唯一可连接组件被误删。
5. 今日锚点决定探索种子和业务问题映射；历史组件只能补齐数据流，不得改变
   `plan_family` 所表达的客户、问题和预期结果。
6. 组合继续执行现有硬门槛：至少 3 个组件、接口依据完整、能力面不重复、数据流
   连通、技术组合成熟度达线、需求证据独立评分、方向冷却有效。
7. 每日仍最多选择 2 个探索方向；没有合格组合时仍输出“本轮无合格方案”。

## 解析修复

将 `可复用型` 加入日报小节类型识别。测试必须证明 `学习型` 后紧邻 `可复用型` 时，
两个项目都被独立解析，字段不会互相覆盖。

## 输出与任务契约

更新 `KUN-TASK.md`：探索方案不再要求所有组件来自今日日报，而是要求至少一个今日
可执行锚点，并允许最近 90 天项目池提供互补组件。报告中的组合理由需区分“今日锚点”
和“历史互补组件”，避免把历史项目表述成今日发现。

不修改需求证据定义，不把项目描述当成用户需求证据；不增加固定模板；不联网补充项目。

## 验证

1. 先补失败测试：`可复用型` 能独立解析。
2. 先补失败测试：今日日报只有一个可执行锚点时，可从 90 天池拼出连通探索组合。
3. 补边界测试：没有可连接历史组件时仍返回空；非执行项目不得入选；组合至少含一个
   今日锚点；近期复用较少的等价组件优先。
4. 运行 `scripts/test_opportunity_analysis.py`。
5. 使用临时输出运行当日 `--check` 和完整生成，确认不会覆盖正式报告，再核对方案数、
   数据流、锚点来源、评分与冷却说明。
6. 运行 `git diff --check`。
