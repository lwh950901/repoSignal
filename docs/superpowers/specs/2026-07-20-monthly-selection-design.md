# RepoSignal 月度精选设计

## 1. 背景

RepoSignal 当前把 `data/github-project-digest` 中的日报和周报构建为静态项目档案。日报负责持续发现，周报负责阶段性筛选，但还缺少一个帮助读者跨项目比较、理解趋势并做出采用决策的月度层级。

月度精选不是四份周报的拼接，也不是单纯按分数排序的榜单。它以人工策展为核心，用候选账本、日报和周报形成入围池，再通过统一的内容结构回答三个问题：本月最值得关注什么、不同读者应该选择什么、下个月前值得采取什么行动。

## 2. 目标

- 每月发布一份可独立分享、可长期归档的静态精选页面。
- 从当月候选中提供 Top 5 深度精选和 8–12 个分类推荐。
- 同时服务独立开发者、技术负责人和 AI 产品创业者。
- 通过明确的入选依据、适用场景和主要风险建立编辑可信度。
- 提供有证据边界的“RepoSignal 本月观察信号”，避免把有限样本包装成全行业结论。
- 复用现有 Markdown、Astro 静态构建和本地搜索体系，不引入数据库或构建期外部 API。

## 3. 非目标

第一版不包含：

- 自动发布月报。
- 实时刷新 GitHub 指标。
- 用户收藏、投票、评论或账号体系。
- 完整候选池和落选项目公开页面。
- 对外展示复杂综合评分或排行榜算法。
- 把搜索结果按仓库聚合。
- 自动生成社交分享图片。

## 4. 产品定位与读者

页面采用“月度编辑部 + 场景选型指南”的组合形态。

每个入选项目设置一个主要适用角色，并可设置最多两个次要角色：

- 独立开发者：关注能否快速试用、是否直接提高个人产出。
- 技术负责人：关注成熟度、风险、团队采用和迁移成本。
- AI 产品创业者：关注产品机会、竞品信号和可组合能力。

角色标签用于帮助读者判断优先级，不为每个角色重复撰写三套项目介绍。只有建议确实存在差异时，才增加角色化说明。

## 5. 内容规则

### 5.1 月份归属

- 项目按其日报发布日期归属自然月，时间口径使用 Asia/Shanghai。
- 月末之后补录的内容进入下一个月，可标注为“上月补充”。
- 月报发布后冻结为当时判断，后续变化在新的月报中说明。
- 页面必须标注数据截止日期。

### 5.2 去重

- 仓库使用小写化后的 `owner/repo` 作为去重键。
- 同一仓库在日报和周报中多次出现时，月报只生成一个项目档案。
- 合并后的记录保留首次发现日期、当月出现次数和最新编辑判断。
- Fork 或用途明显不同的衍生仓库作为独立项目处理。

### 5.3 评选机制

系统先进行硬门槛过滤：

- 仓库可访问，项目定位和许可证基本明确。
- 文档足以让读者判断安装或试用方式。
- 不是明显空壳、重复包装或只有宣传页面的项目。
- 当月存在可验证的采用价值、技术变化或增长信号。
- 没有足以直接否决推荐的安全、维护或合规风险。

编辑再按以下维度比较入围项目：

- 实际可用性。
- 差异化程度。
- 项目成熟度。
- 对目标读者的价值。
- 风险与采用成本。

这些维度只辅助内部判断，不合成为公开的精确总分。页面公开入选依据、适合人群、最佳使用场景、主要风险和建议下一步。

### 5.4 趋势表述

- 对外名称统一使用“RepoSignal 本月观察信号”。
- 一个信号至少由 3 个独立项目支撑，或在不少于 2 个自然周中重复出现。
- 每条信号标注“快速上升”“持续成熟”或“值得观望”，并展示样本数量或时间跨度。
- 证据不足但仍值得记录的判断降级为“编辑观察”，不展示高置信标签。

### 5.5 内容规模

- Top 5 必须恰好包含 5 个项目，每项约 250–400 个中文字符。
- 分类推荐目标为 8–12 个，每项约 60–120 个中文字符；不足时只展示真实项目，不用占位内容补足数量。
- 观察信号为 2–4 条，每条列出支撑项目。
- 三类读者各提供 2–3 条行动建议。
- 整页目标为 3,000–5,000 个中文字符，预计阅读时间 8–12 分钟。

## 6. 页面信息架构

月报采用单页长文，不分页，阅读顺序为：

1. 月度封面：月份、主题、结论摘要和数据截止日期。
2. 本月速览：候选数量、Top 5 数量、分类推荐数量和观察信号数量。
3. 三句话读懂这个月：用三个短结论建立阅读框架。
4. Top 5：第一项完整展开，其余项目保持足够深度但降低视觉重量。
5. 场景选型：分别面向独立开发者、技术负责人和 AI 产品创业者给出推荐组合。
6. 本月观察信号：展示方向、证据强度和支撑项目。
7. 行动建议：为三类读者提供下个月前可执行的动作。
8. 方法说明：说明候选账本初筛、人工定稿和发布后冻结原则。

视觉继续使用现有“研究档案库”语言：纸白背景、墨色正文、苔绿强调、标记黄标签、线性分隔和等宽指标。月报增强封面层级，但不引入渐变、仪表盘或大面积图片。

## 7. 月、周、日导航

站点顶部增加共享的时间粒度切换，顺序为“月 / 周 / 日”。

- 桌面端居中显示三个选项，当前类型使用下边线和字重强调。
- 移动端使用三段式切换，具体月份、周次或日期通过下方选择器切换。
- 月、周、日继续使用独立静态 URL，禁用 JavaScript 时仍可跳转。
- 首页继续默认展示最新周报，以保持当前更新节奏。

切换类型时保留时间上下文。每份报告先转换为时间锚点：

- 月报使用该月最后一天。
- 周报使用 ISO 周的最后一天。
- 日报使用报告日期。

目标选择规则：

- 切到月报时，优先进入包含锚点日期的月份，否则选择不晚于锚点的最近月报。
- 切到周报时，优先进入包含锚点日期的 ISO 周，否则选择结束时间不晚于锚点的最近周报。
- 切到日报时，选择不晚于锚点的最新日报。
- 如果不存在任何目标类型报告，进入该类型的空状态页。

## 8. 数据格式

已发布月报位于：

```text
data/github-project-digest/monthly/YYYY-MM.md
```

自动生成但尚未审核的初稿位于：

```text
data/github-project-digest/monthly-drafts/YYYY-MM.md
```

只有 `monthly/` 参与网站构建。月报沿用 Markdown 和固定中文字段，不增加数据库。规范结构如下：

```md
# 2026 年 7 月精选

> 月度主题：开源 Agent 正从“能运行”走向“可交付”
> 数据截止：2026-07-31
> 候选数量：94

## 本月结论

本月入围项目开始集中解决评测、上下文、编排与团队采用问题。

## Top 5

### 1. pydantic-ai
- 仓库：[pydantic/pydantic-ai](https://github.com/pydantic/pydantic-ai)
- 主要角色：技术负责人
- 次要角色：独立开发者
- 入选依据：在类型约束、结构化输出和测试体验之间形成了清晰的工程边界。
- 最佳使用场景：需要可靠结构化输出与可测试性的生产 Agent 服务。
- 主要风险：快速演进期仍可能出现接口变化。
- 证据强度：高

## 分类推荐

### 独立开发者

- `Egonex-AI/Understand-Anything`：适合探索陌生代码库并建立可交互知识图谱。

## 本月观察信号

### 持续成熟：Agent 工程框架

- 支撑项目：`pydantic/pydantic-ai`、`VoltAgent/voltagent`、`langchain4j/langchain4j`
- 观察：类型、安全、评测与可观测能力正在成为框架的基础能力。

## 行动建议

### 技术负责人

- 为现有 Agent 项目补充权限边界与评测清单。
```

月报解析器只依赖固定标题和字段。允许省略次要角色等可选字段，但月份、主题、数据截止日期、Top 5 项目名、仓库链接、主要角色、入选依据、最佳场景和主要风险是发布必填项。

## 9. 代码结构

月报不复用现有 `ReportView` 的条件分支，而使用独立边界：

- `src/lib/monthly.ts`：月报类型、Markdown 解析、加载和校验。
- `src/components/MonthlyReportView.astro`：月报专属阅读布局。
- `src/components/PeriodSwitcher.astro`：共享的月、周、日切换。
- `src/pages/monthly/index.astro`：最新月报或月报空状态。
- `src/pages/monthly/[month].astro`：历史月报静态页面。
- `scripts/generate_monthly_digest.py`：从候选账本、日报和周报生成初稿。

月报使用独立的 `MonthlyReport`、`MonthlyProject` 和 `MonthlySignal` 类型，避免给日报和周报模型增加大量可选字段。站点框架、视觉令牌、仓库链接和搜索索引仍然共享。

## 10. 数据流与发布流程

```text
候选账本 + 日报 + 周报
          ↓
按自然月聚合，按 owner/repo 去重
          ↓
应用硬门槛并生成 monthly-drafts/YYYY-MM.md
          ↓
编辑确定 Top 5、角色、风险、观察信号和行动建议
          ↓
运行月报校验
          ↓
移动到 monthly/YYYY-MM.md
          ↓
Astro 构建静态页面与搜索索引
```

构建阶段不访问 GitHub API。生成器使用仓库内已有数据，因此旧页面可重复构建，外部网络故障不会阻断部署。

## 11. 搜索与归档

- 月报项目加入现有 `⌘K / Ctrl+K` 本地搜索索引。
- 搜索结果增加“月 / 周 / 日”类型标记。
- 同一仓库有多期记录时保留各条历史记录，但月度精选排在日报和周报之前。
- 第一版不增加筛选面板，也不把结果聚合为单一仓库页。
- 桌面端月报显示月份归档，移动端使用月份选择器。
- 月报提供上一月和下一月链接。

## 12. 异常与降级

- 月份、主题、截止日期或 Top 5 缺失时，月报校验失败，不允许作为已发布内容构建。
- Top 5 仓库链接不是合法 GitHub URL 时，校验失败并指出项目位置。
- 同一仓库在一份月报中重复出现时，校验失败并报告重复位置。
- 分类推荐缺少可选字段时隐藏对应字段，不阻断页面。
- 观察信号缺少足够支撑时降级为“编辑观察”。
- 没有任何月报时，月度入口展示内容说明和空状态，不伪造榜单。
- 项目结构化解析失败但仍有可读 Markdown 时，保留原始正文作为诊断性降级内容；必填字段错误仍由发布校验阻止。
- JavaScript 不可用时，正文、周期导航、月份导航和 GitHub 链接保持可用。

## 13. 性能、SEO 与无障碍

- 月报正文由 Astro 静态渲染，不增加客户端框架。
- 页面新增 JavaScript 仅限复用现有搜索功能。
- 不增加大型图片或额外字体资源。
- 每期生成独立标题、描述和 canonical URL，例如 `/monthly/2026-07/`。
- Open Graph 使用月度主题和编辑结论摘要；第一版不生成专属分享图片。
- 页面保持正确的 `h1`、`h2`、`h3` 层级和月份时间语义。
- 所有链接与切换项有可见键盘焦点，颜色对比沿用现有令牌。
- 360px 宽度下不得出现横向滚动。
- 尊重 `prefers-reduced-motion`，月报不增加必要性不足的动效。

## 14. 测试策略

单元测试覆盖：

- 月报 Markdown 解析与必填字段校验。
- `owner/repo` 大小写归一化和项目去重。
- Top 5 数量校验和非法 GitHub URL。
- 观察信号证据降级。
- 月、周、日时间锚点和缺失报告回退。
- 搜索索引中的类型标识和月报优先级。

集成与构建检查覆盖：

- 月报索引页和历史静态路径生成。
- 顶部周期切换、月份归档和上一月/下一月链接。
- 月报空状态和字段缺失降级。
- 关闭 JavaScript 后的核心导航与正文阅读。
- 360px 移动端无横向溢出。
- `npm test`、`npm run check` 和 `npm run build` 全部通过。

## 15. 验收标准

- `data/github-project-digest/monthly/*.md` 能生成对应的静态月报页面。
- 月报包含封面结论、Top 5、分类推荐、观察信号和行动建议。
- Top 5 每项展示主要角色、入选依据、最佳场景和主要风险。
- 顶部可在月、周、日之间切换，并按照规则保留时间上下文。
- 桌面和移动端均可浏览历史月份。
- 月报项目可通过现有命令搜索找到，结果有明确类型标记。
- 无月报、可选字段缺失和无 JavaScript 状态均有可用降级。
- 发布流程使用自动初稿和人工定稿，不会意外构建 `monthly-drafts/`。
- 月报解析、去重、周期映射和搜索索引具有自动化测试。
- 测试、类型检查和生产构建全部通过。
