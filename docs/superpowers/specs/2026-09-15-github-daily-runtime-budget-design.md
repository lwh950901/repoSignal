# GitHub 日报运行时预算与低 Token 设计

## 目标

- 模型保持 `gpt-5.6-terra`、`high`，不以换模型换取速度。
- 日报通常在 60 分钟内完成，最长运行 90 分钟。
- 运行到 30、60 分钟时必须根据本地检查点检查实际进度；连续 15 分钟无进展时停止当前扩展并降级。
- 保留四类正式推荐、实时证据、评分权重、十字段、90 天去重、用户候选和原子 finalize，尽可能保持日报质量不变。
- 将模型看到的候选限制为每类最多 3 个，将模型/工具往返压缩为少量批次，累计输入 Token 目标不超过 60 万。
- 仍然只有 05:00 一次计划运行；失败后保留检查点，禁止自动补跑。

## 架构

### 运行检查点

扩展 `scripts/daily_digest_checkpoint.py`，在 `daily-runs/YYYY-MM-DD.json` 中保存：

- `startedAt`、`lastProgressAt`、`deadlineAt`；
- 当前 `stage`、候选数、已核验数和最多五条错误；
- 根据耗时返回的 `action`：继续发现、停止扩大搜索、开始写日报、停止附加工作、立即收尾或停止；
- 连续 15 分钟无进展时返回 `stalled: true`。

所有时间判断使用 UTC 时间戳和单调的阶段规则。`start` 幂等，恢复任务不得重置原始开始时间。

### 单入口发现与紧凑证据包

新增 `scripts/daily_digest_runner.py`：

1. `discover` 在一次进程中并发运行六条固定上限的 GitHub Search；每条最多 12 项，TLS 只允许一次 `--insecure` 重试。
2. 发现结果按正确 lane 原子写入候选账本，并合入未解决的用户候选占位。
3. `shortlist` 在模型参与前过滤归档、许可证不明确和 90 天重复候选，按四类各保留最多 3 个，输出紧凑 JSON；用户候选保留并明确重复状态。
4. 命令在本地更新进度检查点，超出阶段预算时停止扩展并使用本轮已有结果。

模型仍负责最终类型判断、实时证据复核、评分与写作；本地预筛只移除已被现有硬规则明确拒绝的项目，避免降低推荐质量。

### 自动化协议

缩短 `docs/automation-prompts/github-daily.md`：只保留结果合同、质量门槛、统一 runner 命令、时间闸门和降级规则。禁止读取脚本源码、完整候选、完整 history、完整 trial-status 或历史归档。模型只读取紧凑 `inspect`、`shortlist` 和最终 enrichment 摘要。

时间闸门：

- 30 分钟：停止扩大搜索，使用已有候选；
- 60 分钟：强制进入日报草稿与 finalize；
- 85 分钟：立即降级收尾；
- 90 分钟：停止运行并保留检查点。
- 到期预算不得由自动化自行重置；人工显式执行 `daily_digest_checkpoint.py resume` 后，保留阶段、计数和错误摘要并开启新的 90 分钟续跑预算。

日报自动化的职责止于日报 finalize 与验证；独立下游任务不由日报模型触发、等待、检查或汇报。

## 质量保护

- 六个发现通道、每条 12 项上限保持不变。
- 正式推荐仍为 4–5 项，前四项依次为爆发型、实用型、潜力型、学习型。
- 评分权重、爆发型数值门槛、十字段、许可证和 90 天去重不变。
- shortlist 每类保留三个候选并标注被过滤原因计数；模型可以从当日完整候选账本精确查找某个候补，但禁止输出或读取全文。
- finalize 前必须先运行去重检查，避免写完草稿后才发现候选冲突。

## 验收

- 新增测试覆盖 30/60/75/85/90 分钟动作、15 分钟停滞、普通恢复不重置开始时间、人工 resume 重置预算、候选预筛、每类上限、用户候选和 90 天去重。
- 现有 checkpoint、自动化契约、候选账本和可行性测试继续通过。
- 自动化保持 ACTIVE、原 RRULE、`gpt-5.6-terra/high`。
- 仓库提示词与已安装自动化提示词一致。
