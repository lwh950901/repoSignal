# GitHub 优质项目发现任务设计

## 目标

持续发现值得使用、学习或二次开发的 GitHub 项目。推荐不以 Star 数量单独排名，兼顾热门增长、成熟实用和小众潜力，并通过用户反馈逐步校准偏好。

## 运行时间

- 周一至周六 05:30（Asia/Shanghai）：每日推荐 4–5 个新项目。
- 周六 07:30（Asia/Shanghai）：发布本周深度精选。
- 周日不运行。

系统由两个独立自动任务组成：每日发现任务和每周精选任务。

## 搜集范围

主题覆盖：

- AI、Agent、RAG；
- 全栈应用、开发工具；
- 不限领域的优秀跨界项目。

来源包括 GitHub Trending、Search、Topics、新项目与新版本，以及可信技术社区中的发现线索。Awesome 清单、提示词库、Skills、教程合集、评测和研究资源可以作为候选来源或额外发现，也允许在质量特别高时进入主推荐，但必须明确说明其内容类型。内容型项目每天最多占用一个主推荐位置；若当天还有其他达到质量门槛的内容型项目，应放在三个主推荐之后的“额外发现”，不得挤占其余软件、模型或数据项目位置。

## 候选筛选与评分

每天建立候选池，核验 GitHub 仓库的实时信息，并按以下维度综合判断：

- 社区信号 25%：Stars、Forks、采用情况、讨论热度和增长趋势；
- 维护状态 25%：近期有效提交、Release、Issue/PR 响应及是否归档；
- 项目质量 20%：README、文档、示例、测试、CI 和架构清晰度；
- 用户适合度 20%：是否适合直接使用、技术学习或二次开发；
- 风险 10%：许可证、维护中断、项目成熟度、依赖和潜在安全风险。

社区数据只是信号，不按 Star 单独排序。优先选择活跃、可理解、有明确价值和扩展空间的项目。

主推荐排除归档仓库、纯镜像、明显玩具 Demo，以及许可证不明且会造成实际使用风险的项目。每日正式推荐最少 4 个、最多 5 个；“额外发现”独立计算，不计入正式推荐数量。无法核实的数据应明确标注，不得猜测。

## 每日输出

每日前四个主推荐位置原则上分别为：

1. 爆发型：近期增长或讨论明显加速；
2. 实用型：成熟、可部署或可直接投入工作；
3. 潜力型：新颖、小众、有学习或二次开发价值。
4. 学习型：架构、实现、评测或工程取舍具有明确拆解价值，适合阅读源码、复现或专题学习；不要求能够直接投入生产，但必须标明实现新鲜度与照搬风险。

每日正式推荐必须至少包含 1 个爆发型。爆发型必须有 GitHub Trending、近期增长、显著讨论或新版本带来的可核验加速证据；不能只因 Stars 总量高而标记为爆发型。若当天没有同时满足实时核验、质量门槛和爆发证据的项目，必须报告“爆发型位置阻塞”，不得用未经核验或仅凭总 Stars 的项目凑位。

爆发型的增长证据采用以下数值口径：

- 爆发型硬下限：实时核验的当前 Stars 必须达到至少 5,000；低于 5,000 Stars 的项目即使相对增幅很高，也只能归入潜力型或额外发现，不能占用爆发型位置。
- “近 48 小时显著增长”：必须有相隔 36–60 小时的两次 GitHub 实时快照，并按起始 Stars 分档，同时满足绝对增量与相对增幅：起始不足 1,000 Stars 时至少新增 200 且增长不少于 30%；起始为 1,000–9,999 Stars 时至少新增 500 且增长不少于 20%；起始达到 10,000 Stars 时至少新增 1,000 且增长不少于 10%。
- “近期显著增长”：默认观察窗口为 7 天，必须有两次实时快照或可核验事件序列，并按起始 Stars 分档，同时满足：起始不足 1,000 Stars 时至少新增 500 且增长不少于 50%；起始为 1,000–9,999 Stars 时至少新增 1,500 且增长不少于 30%；起始达到 10,000 Stars 时至少新增 3,000 且增长不少于 20%。
- 新建项目补充口径：仓库创建不超过 48 小时且达到至少 5,000 Stars，或创建不超过 7 天且达到至少 5,000 Stars，可作为增长证据，但仍必须有实时仓库事实、质量证据和风险核验；不得把单一快照冒充时间序列增长。
- Trending、显著讨论或重大版本/Release 可以作为其他加速证据，但必须记录可核验日期、事件和影响；没有上述增长数字时，不能仅凭总 Stars、最近 pushed_at 或无日期的 Release 标签判定爆发型。

四类类型的筛选调节如下；类型门槛用于决定候选能否进入该类，五维综合评分仍统一使用社区信号 25%、维护状态 25%、项目质量 20%、用户适合度 20%、风险 10%。

- 共用硬门槛：必须完成 GitHub 实时核验；不得归档、纯镜像、明显玩具化；许可证必须明确，或至少已核实不会造成实际使用风险；必须有至少 1 条维护证据和 2 条质量证据。正式推荐综合分原则上不低于 80/100；70–79 分只能作为额外发现或在报告中明确说明例外。
- 爆发型：在共用硬门槛之外，当前实时 Stars 必须至少 5,000，并满足既定的 48 小时/7 天增长阈值，或有日期明确的 Trending、显著讨论、重大版本/Release 加速证据。总 Stars 只能作为下限和背景，不能单独加满该类型。
- 实用型：必须能说明“现在如何用”。安装/启动说明和可运行示例为必需；以下生产就绪信号至少满足 3 项：测试、CI、稳定 Release、完整文档、可复用示例、持续 Issue/PR 维护。最近 90 天内还必须有至少 1 项有意义活动；重点看维护状态、质量和直接投入工作的适合度。
- 潜力型：不设 Stars 下限，通常优先关注低于 5,000 Stars 但有明确新颖性或扩展空间的项目；最近 60 天内至少有 1 项有意义活动；必须指出一个具体差异化亮点和可行的二次开发路径，并满足至少 2 条质量证据。不能把“刚创建”本身当作潜力价值，也不能用停更项目凑位。
- 学习型：不要求生产就绪或 Stars 门槛，但必须明确指出至少 1 个可拆解对象（架构、模块、算法、评测或工程实践），并提供至少 1 个可复现学习入口（示例、测试、基准、运行说明或结构化文档）。质量证据必须具体说明实现新鲜度；风险字段必须写明哪些做法不宜直接照搬。非归档项目最近 180 天内应有代码、Release 或文档活动；若无，则必须解释其仍具学习价值的原因。

类型冲突时按主要价值归类：近期加速优先爆发型；可直接部署优先实用型；新颖性和二次开发优先潜力型；源码拆解价值优先学习型。第 5 个正式位置可以复用类型，但必须说明复用理由。

每天设置一个重点主题，但不限制其他正式推荐位置的领域。前四个正式推荐原则上对应爆发型、实用型、潜力型、学习型；第 5 个可复用这四类标签，按项目的真实价值归类。学习型不能仅因教程性 README 入选，必须能够指出具体可学习的架构、模块、算法、评测或工程实践，以及哪些实现不宜直接照搬。每个项目包含：

- 仓库链接和一句话定位；
- 类型与适合用途；
- 核心亮点和适用场景；
- 主要技术栈；
- Stars、Forks、近期有意义的活动与许可证；
- 质量证据、潜在风险和推荐理由。

报告末尾选择“今天最值得亲自试用的一个”。正式推荐之外，可追加 0–2 个额外发现，且额外发现不计入每日正式推荐的 4–5 个上限。Awesome 清单、教程合集或其他优质线索可作为额外发现附在末尾，不强行占用正式推荐名额。额外发现同样必须使用五维综合评分，标题统一为 `### 额外发现：owner/repo — 分数/100`，并完整包含与主推荐相同的十个证据字段；内容型项目的“项目质量”应按来源可追溯性、结构完整性、更新机制和可复用性判断，不机械要求软件项目的测试与 CI。

### 每日报告固定格式

日报必须使用以下机器可解析结构。标题层级、字段名、字段顺序、中文冒号和评分位置不得改变；字段名不得加粗。正文内容可按实际情况扩展，但这些字段不可缺失。

```markdown
# GitHub 优质项目每日发现｜YYYY-MM-DD

> 今日重点：一句话主题说明。

## 今日结论

本日结论。

## 主推荐

### 1. 爆发型：owner/repo — 82/100

- 仓库：[owner/repo](https://github.com/owner/repo)
- 一句话定位：项目定位。
- 类型与适合用途：类型和适用对象。
- 核心亮点与场景：核心价值。
- 主要技术栈：技术一、技术二。
- 实时指标：Stars / Forks、许可证和仓库状态。
- 近期有意义活动：提交或 Release 证据。
- 质量证据：1–3 条证据。
- 风险：真实风险。
- 推荐理由：推荐原因。

### 2. 实用型：owner/repo — 88/100

同样字段。

### 3. 潜力型：owner/repo — 84/100

同样字段。

### 4. 学习型：owner/repo — 86/100

同样字段，并在质量证据和风险中说明值得拆解的实现与不宜照搬之处。

## 今天最值得亲自试用

项目和理由。
```

写入前必须自检：正式推荐标题均匹配 `### 序号. 爆发型/实用型/潜力型/学习型：owner/repo — 分数/100`，正式推荐数量为 4–5，且前四项分别为爆发型、实用型、潜力型、学习型；每项均包含仓库、一句话定位、主要技术栈、风险和推荐理由；学习型还必须明确具体学习价值与不宜照搬之处；若有额外发现，最多 2 项且每项也包含十个证据字段，额外发现不计入正式推荐数量。

## 候选账本

每次每日运行完成时，系统应将扫描器发现的全部候选仓库写入 `data/github-project-digest/candidates/YYYY-MM-DD.jsonl`，每行一个 JSON 对象、每个规范化仓库仅出现一次。

### 候选记录字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `date` | string | 发现日期 |
| `repo` | string | 规范化小写 `owner/repo` |
| `url` | string | GitHub 仓库 URL |
| `lanes` | string[] | 发现通道（如 growth、mature、emerging） |
| `sources` | string[] | 发现来源（如 trending、search、topic） |
| `stars` | int or null | 发现时的 Stars 数 |
| `forks` | int or null | 发现时的 Forks 数 |
| `license` | string or null | SPDX 许可证标识 |
| `archived` | bool | 是否已归档 |
| `pushed` | string or null | 最近推送时间 |
| `status` | string | 处置状态：`discovered` / `shortlisted` / `rejected` / `primary` / `extra` |
| `verified` | bool | GitHub 事实是否已核验 |
| `reason` | string or null | 处置原因（rejected/primary/extra 必须非空） |

### 规范化与去重

- 仓库名按大小写不敏感规范化，首现保留，后现合并 `lanes` 和 `sources`。
- 后出现的非空 GitHub 事实覆盖前值。
- 输出按 `repo` 字段确定性排序。
- 使用 Python 标准库，原子写入（先写 `.tmp` 再 `os.replace`）。

### 处置流程

1. 写入时所有记录 `status: discovered`、`verified: false`。
2. 短列表阶段更新 `status: shortlisted`。
3. 最终发布前更新 `primary` 和 `extra` 记录为 `verified: true` 并填写 `reason`。
4. 被排除的候选更新为 `rejected` 并填写原因。

### 关联数据

- `history.jsonl` 记录主推荐和额外发现的 `role` 字段（`primary` / `extra`），不存储完整候选池。
- 候选账本不保存在 `history.jsonl` 中，仅在日期键文件中存储。

## 每周精选

周六 07:30 从当周周一至周六的全部主推荐与额外发现中深度精选恰好 10 个，不再搜索一批新项目替代本周候选。周精选任务必须读取每日 Markdown 报告中的 `## 主推荐` 和 `## 额外发现` 两个部分；日报分数和位置只作为初筛信号，周末仍需统一复核后重新排序，额外发现与主推荐具有同等入选资格。

精选报告补充阅读 README、Issue、Release 和近期提交，说明维护健康度、真实风险、上手建议，以及它为何值得进入本周精选。每周精选固定为 10 个；若同周日报中不足 10 个候选通过硬门槛，必须报告阻塞，禁止搜索新仓库补位、编造候选或发布不完整周报。

### 每周报告固定格式

周报项目统一使用二级标题，字段名和顺序不得改变，字段名不得加粗：

```markdown
# GitHub 优质项目每周精选｜YYYY-Www

本周摘要。

## 1. 项目名

- 仓库：[owner/repo](https://github.com/owner/repo)
- 项目简介：用 1–2 句说明项目面向谁、解决什么问题，以及以何种软件、框架、工具或内容形态交付；不写指标、入选判断或营销式评价。
- 入选理由：入选原因。
- 质量与维护：质量证据和维护健康度。
- 主要技术栈：技术一、技术二。
- 实时指标：Stars / Forks 和许可证。
- 真实风险：主要风险。
- 上手建议：如何试用。
- 本周精选价值：为什么进入精选。
```

写入前必须自检每个项目均包含仓库、项目简介、入选理由、质量与维护、主要技术栈、实时指标、真实风险、上手建议和本周精选价值。仓库必须位于项目字段首位，项目简介必须位于仓库之后、入选理由之前。

## 去重与状态

- 主推荐默认 90 天内不重复。
- 发生重大版本发布、显著增长或项目方向转型时允许再次推荐，但必须说明新变化。
- 每日任务在历史文件中记录主推荐的日期、类型、关键指标和推荐理由，供 90 天去重；额外发现保留在每日 Markdown 报告中，由周精选直接读取并纳入候选池。
- 已停止维护或质量明显下降的项目不进入周精选。

## 偏好反馈

发现真正高质量的项目始终是最高优先级。每个项目提供“收藏 / 一般 / 不感兴趣”三个反馈选项，但标注只作为次级信号：仅当多个候选的核心质量和发现价值接近时，才用于微调主题、成熟度、技术栈和项目类型的排序。

反馈不得降低质量门槛，也不得将推荐固化在用户已经熟悉的领域。每日候选池仍需主动保留跨领域、小众和意外发现，以避免形成兴趣茧房。

## 异常处理

- GitHub 或外部来源暂时不可用时，不使用未经核实的缓存事实冒充实时信息；报告应说明受影响的数据。
- API 限流时减少候选数量或改用可核实的网页信息，不猜测指标。
- 历史记录不可读取时暂停去重相关结论，并明确提示状态异常。
- 自动任务失败时保留错误摘要，下一次运行继续正常周期，不补发重复报告。

## 验证标准

创建任务后先进行一次受控试运行，确认：

- 四类项目区分清楚；
- 所有链接和关键指标可核实；
- 输出字段完整且篇幅适中；
- 90 天去重记录可以写入和读取；
- 周精选能够读取同一周的每日结果；
- 用户反馈能够被记录并影响后续排序。

试运行通过后，两个任务按正式时间表运行。
