# GitHub 优质项目发现任务设计

## 目标

持续发现值得使用、学习或二次开发的 GitHub 项目。推荐不以 Star 数量单独排名，兼顾热门增长、成熟实用和小众潜力，并通过用户反馈逐步校准偏好。

## 运行时间

- 周一至周六 08:30（Asia/Shanghai）：每日推荐 3 个新项目。
- 周六 10:30（Asia/Shanghai）：发布本周深度精选。
- 周日不运行。

系统由两个独立自动任务组成：每日发现任务和每周精选任务。

## 搜集范围

主题覆盖：

- AI、Agent、RAG；
- 全栈应用、开发工具；
- 不限领域的优秀跨界项目。

来源包括 GitHub Trending、Search、Topics、新项目与新版本，以及可信技术社区中的发现线索。Awesome 清单和教程合集可以作为候选来源或额外发现，也允许在质量特别高时进入主推荐，但必须明确说明其内容类型。

## 候选筛选与评分

每天建立候选池，核验 GitHub 仓库的实时信息，并按以下维度综合判断：

- 社区信号 25%：Stars、Forks、采用情况、讨论热度和增长趋势；
- 维护状态 25%：近期有效提交、Release、Issue/PR 响应及是否归档；
- 项目质量 20%：README、文档、示例、测试、CI 和架构清晰度；
- 用户适合度 20%：是否适合直接使用、技术学习或二次开发；
- 风险 10%：许可证、维护中断、项目成熟度、依赖和潜在安全风险。

社区数据只是信号，不按 Star 单独排序。优先选择活跃、可理解、有明确价值和扩展空间的项目。

主推荐排除归档仓库、纯镜像、明显玩具 Demo，以及许可证不明且会造成实际使用风险的项目。若当天高质量项目不足 3 个，允许少推荐，不以低质量候选凑数。无法核实的数据应明确标注，不得猜测。

## 每日输出

每日 3 个位置原则上分别为：

1. 爆发型：近期增长或讨论明显加速；
2. 实用型：成熟、可部署或可直接投入工作；
3. 潜力型：新颖、小众、有学习或二次开发价值。

每天设置一个重点主题，但不限制另外两个位置的领域。每个项目包含：

- 仓库链接和一句话定位；
- 类型与适合用途；
- 核心亮点和适用场景；
- 主要技术栈；
- Stars、Forks、近期有意义的活动与许可证；
- 质量证据、潜在风险和推荐理由。

报告末尾选择“今天最值得亲自试用的一个”。Awesome 清单、教程合集或其他优质线索可作为额外发现附在末尾，不强行占用三个主推荐名额。

## 每周精选

周六 10:30 从当周周一至周六最多 18 个主推荐中深度精选最多 5 个，不再搜索一批新项目替代本周候选。

精选报告补充阅读 README、Issue、Release 和近期提交，说明维护健康度、真实风险、上手建议，以及它为何值得进入本周精选。质量不足时允许少于 5 个。

## 去重与状态

- 主推荐默认 90 天内不重复。
- 发生重大版本发布、显著增长或项目方向转型时允许再次推荐，但必须说明新变化。
- 每日任务记录推荐日期、类型、关键指标和推荐理由，供去重和周精选读取。
- 已停止维护或质量明显下降的项目不进入周精选。

## 偏好反馈

发现真正高质量的项目始终是最高优先级。每个项目提供“收藏 / 一般 / 不感兴趣”三个反馈选项，但标注只作为次级信号：仅当多个候选的核心质量和发现价值接近时，才用于微调主题、成熟度、技术栈和项目类型的排序。

反馈不得降低质量门槛，也不得将推荐固化在用户已经熟悉的领域。每日候选池仍需主动保留跨领域、小众和意外发现，以避免形成兴趣茧房。

## 异常处理

- GitHub 或外部来源暂时不可用时，不使用未经核实的缓存事实冒充实时信息；报告应说明受影响的数据。
- API 限流时减少候选数量或改用可核实的网页信息，不猜测指标。
- 历史记录不可读取时暂停去重相关结论，并明确提示状态异常。
- 自动任务失败时保留错误摘要，下一次运行继续正常周期，不补发重复报告。

## 验证标准

创建任务后先进行一次受控试运行，确认：

- 三类项目区分清楚；
- 所有链接和关键指标可核实；
- 输出字段完整且篇幅适中；
- 90 天去重记录可以写入和读取；
- 周精选能够读取同一周的每日结果；
- 用户反馈能够被记录并影响后续排序。

试运行通过后，两个任务按正式时间表运行。
