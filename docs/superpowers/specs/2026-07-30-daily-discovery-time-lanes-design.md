# GitHub 日报候选时间通道修复设计

## 背景

日报候选发现曾把最近 10–15 天创建作为部分新锐查询的硬条件。该窗口过短，会在项目刚形成文档、Release、用户和工程证据时将其排除。与此同时，较早创建但持续维护或重新活跃的项目也需要稳定的发现入口。

仓库年龄不等于项目价值。本修复将创建时间限定为新锐发现信号，不再让它影响整个候选池的资格。

## 范围

本次只修改后续的“GitHub 优质项目每日发现”任务及其设计基线。

- 不修改 2026-07-30 及更早日报。
- 不修改周报自动化；周报继续只复核本周日报已有候选。
- 不修改月报自动化；月报继续汇总整月已有日报、周报、候选账本和研究材料。
- 不为任何具体仓库增加专属搜索或保底规则。
- 不改变每日 3–5 个正式推荐、0–2 个额外发现、五维评分、90 天推荐去重和固定输出格式。

## 时间通道

日报实时搜索至少包含以下互补时间通道。各通道只保证执行和合并候选，不保证占用正式推荐位置。

### 新锐项目

用于发现已经有机会形成可核验证据的早期项目。

- 使用 Asia/Shanghai 当天动态计算最近 90 天创建窗口。
- 查询可以使用 `created:>90天前`。
- 同时要求最近 30 天有推送，或在精确核验时确认最近 30 天有有意义 Release/Commit。
- `created:>` 只允许出现在该通道及明确标记的新项目补充查询中。

### 常青实用项目

用于发现较早创建但仍值得直接使用、学习或二次开发的项目。

- 不得使用 `created` 限制。
- 优先搜索最近 90 天仍有推送的项目。
- Stars 可以用于扩大或缩小搜索结果，但不得成为单独排名依据。
- 最终维护判断必须结合 Release、Commit、Issue/PR、文档、测试和许可证。

### 老项目复兴

用于发现较早创建、近期重新出现实质变化的项目。

- 可以在明确标记的复兴补充查询中使用 `created:<90天前` 帮助定位旧仓库，但该日期只用于发现，不参与评分或排除。
- 优先检查最近 30 天恢复提交、发布重大版本、显著增长、维护组织变化或方向转型。
- 只有能够说明“最近发生了什么”的项目才可按复兴信号进入爆发型或实用型评估。

### 其他既有通道

GitHub Trending、通用增长、当日重点主题、AI/Agent/RAG、全栈/开发工具、Topics 和跨领域发现继续执行。

- 这些核心通道不得使用 `created` 作为候选门槛。
- 当日重点主题必须至少执行一条不含 `created` 的查询。
- 单个查询结果上限不能替代分层发现；各通道结果先独立获取，再规范化合并。

## 候选合并与评分

所有通道发现的仓库写入同一个当日候选账本：

- 仓库名按大小写不敏感规范化，首现保留，后续来源和通道合并。
- 新锐、常青和复兴只写入 `lanes`/`sources`，不产生额外分数或推荐配额。
- 仓库年龄不加分也不扣分。
- 当前维护、项目质量、用户适合度、社区信号和风险继续按既有五维权重评分。
- 旧项目只保证进入候选发现，不保证正式入选；新项目同样不享有保底推荐位。

## 覆盖自检

日报写入前必须检查：

1. 新锐通道使用的创建窗口是否为最近 90 天，而不是 10–15 天。
2. 除明确标记的新锐或复兴补充查询外，其他核心查询是否均不含 `created`。
3. 常青实用和老项目复兴通道是否实际运行，并记录查询结果数。
4. 当日重点主题是否至少有一条不含 `created` 的精准查询。
5. 各通道候选是否完成规范化合并，用户指定候选是否保留。
6. 最终结果是否说明各时间通道、查询结果数、扫描器状态和降级路径。

若某个通道因查询过窄返回空结果，允许放宽非时间关键词重试一次；不得通过缩短或扩大日期窗口临时操纵结果。GitHub/API 不可用时遵循现有降级规则，未核实缓存不得冒充实时事实。

## 验证

实施完成后执行以下检查：

- 设计基线和日报自动化都明确新锐 90 天、近期活跃 30 天。
- 日报自动化明确常青、复兴及其他核心通道不受 `created` 限制。
- 周报和月报自动化内容、计划和状态保持不变。
- 日报固定格式、五维评分、历史去重和候选账本合同没有被修改。
- 使用示例查询做一次不写日报的扫描验证，确认新锐、常青和复兴三类候选均能返回或明确报告空结果。

## 成功标准

后续日报不会因为仓库稍早创建而失去候选资格；新项目仍有独立发现入口，长期活跃和重新复兴的旧项目也能进入统一候选池，并由质量而不是年龄决定是否推荐。
