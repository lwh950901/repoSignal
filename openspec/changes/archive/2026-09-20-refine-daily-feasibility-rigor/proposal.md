## Why

每日可行性方案已经能稳定产出，但报告的可信度没有被约束：单一“方案评分”把组件成熟度当成商业可行性，方案允许只有标签相关的组合，MVP 没有可证伪口径，同一方向可以连续多天换标题复现，市场与需求表述里出现“刚需/愿意付费”这类没有来源的结论，还自动生成了“单点项目机会”这种低价值内容。结果是“每天都有产出”，但可选方案的质量与可验证性不足。

本变更把报告改成“少而可信、能够验证”的口径：允许当天没有合格方案，用两个互不合并的评分和四档判断替代单一评分与“优先推进最高分”，并要求每个方案给出完整数据流与可证伪的 MVP 实验。生成脚本与任务规则同时修改，仅改文案不足以解决根本问题。

## What Changes

- **组合闭环门槛**：每个方案必须给出可连接的组件数据流（起点 → 处理 → 终点）、每个组件的输入输出与接入方式；组件少于 3 个、缺接口依据（仅标签相关）、能力面重复或数据流不连通的组合直接剔除，并在今日结论里计数说明。
- **拆分评分**：`技术组合成熟度`（组件可靠度 40 · 组件供给 20 · 风险敞口 20 · 许可证 10 · 完整度 10）与 `需求证据强度`（证据等级 40 · 用户明确表态 25 · 独立来源 20 · 新鲜度 15）分别 0-100，不再合并。
- **四档方案判断**：值得用户访谈 / 值得技术试验 / 继续观察 / 暂不建议；取消“优先推进最高分方案”，“暂不建议”不进入方案列表。
- **可证伪 MVP**：每个方案给出测试场景、测试数据、周期、成功指标、失败指标与停止条件。
- **跨日冷却**：同一 `plan_family` 冷却 7–14 天；冷却中段只有新增关键组件、证据等级提升或客户问题变化才允许提前重现，并在今日结论里说明理由。
- **证据等级标注**：需求与市场表述区分“已确认事实 / 项目方自述 / 待验证假设 / 无证据”，禁止“刚需、愿意付费、市场已验证”等无来源断言（生成侧清洗 + 测试校验）。
- **精简与重排**：删除“单点项目机会”与笼统“行动建议”；报告按 `今日结论 → 方案判断 → 客户问题 → 组件数据流 → 双评分 → MVP 实验 → 最大不确定性 → 下一步动作` 组织。
- **网页呈现与兼容**：详情页展示方案判断与双评分面板，摘要字段改为方案判断 / 目标客户 / 需求证据；历史报告（单一评分、单点机会、行动建议）继续按原格式渲染。

### Modified Capabilities

- `daily-feasibility-reports`: 生成侧新增闭环门槛、双评分、四档判断、可证伪 MVP、7–14 天冷却与证据等级标注，并重排/精简报告结构；构建侧解析并展示方案判断与双评分，同时保留历史报告兼容。

## Impact

- `scripts/opportunity_analysis.py`：评分拆分为两套、闭环门槛与能力面 I/O 交接表、证据等级与证据采集、四档判断、MVP 实验生成、冷却判定、章节重排、删除单点机会与行动建议。
- `scripts/test_opportunity_analysis.py`：更新与新增闭环门槛、双评分、判断阶梯、证据等级、冷却、报告结构与 KUN-TASK 契约测试。
- `data/github-project-digest/feasibility/KUN-TASK.md` 与 Kun 定时任务入口提示：同步新口径（0–3 个方案、双评分、四档判断、闭环门槛、冷却、证据等级）。
- `src/lib/feasibility.ts`、`src/components/FeasibilityReportView.astro`、`src/styles/global.css` 及相关测试：解析与展示双评分与方案判断，保持历史报告兼容。
- 不新增运行时依赖，不修改历史报告文件，不改变 `plan_family` / `variant` 定义。
