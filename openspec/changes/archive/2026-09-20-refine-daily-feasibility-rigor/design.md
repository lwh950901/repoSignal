## Context

生成器 `scripts/opportunity_analysis.py` 的输入是最近 90 天的日报/周报项目池与当天日报锚点，输出是单份 Markdown 可行性报告，供定时任务（Kun 06:30）与静态站点（`/feasibility/<date>/`）消费。任务规则写在 `data/github-project-digest/feasibility/KUN-TASK.md`，入口提示在 Kun 定时任务里。

现有口径的问题：单一综合分把“组件能不能拼”直接当成“方案值不值得做”；组合允许只是能力面标签相关；MVP 只有一句“先试用”；同一 `plan_family` 只限制连续两天，可以隔一天再出现；需求侧只有模板文案，没有任何等级标注。

约束：全部判定必须是确定性的（同一输入产出同一报告，可复现、可测试）；不得引入新的运行时依赖；不得改动历史报告文件；`plan_family` / `variant` 的定义保持不变，跨日冷却与周报选择器继续依赖它。

## Goals / Non-Goals

**Goals**

- 让“组合成立”有硬门槛：组件 ≥3、每个组件有源报告接口依据、能力面不重复、数据流按交接表连通且有起终点。
- 把两个问题分开打分并给出四档判断，让“技术成熟但需求无证据”只会落到技术试验或继续观察，而不会被称为可行。
- 让每个方案都能被证伪：场景、数据、周期、成功指标、失败指标、停止条件。
- 让同一方向在 7–14 天内不靠换标题反复出现。
- 让需求与市场表述带证据等级，删掉无来源断言与低价值章节。

**Non-Goals**

- 不做客户访谈、不联网核验 GitHub、不引入真实付费或预算数据。
- 不改变候选项目池的来源与解析规则（日报/周报格式不变）。
- 不重做站点信息架构；只调整详情页的摘要字段与评分面板。
- 不为历史报告重算分数或补写新字段。

## Decisions

**1. 闭环门槛用“能力面 I/O + 交接表”而不是自由文本**
`CAPABILITY_IO` 为 12 个能力面定义输入/输出，`CAPABILITY_HANDOFFS` 定义允许的上下游交接，`DEPLOY_FACES`（local）只作部署形态、不参与连通性。判定：组件数 ≥ `MIN_PLAN_COMPONENTS`(3)、每个组件通过 `interface_evidence()`（源报告的亮点/上手/类型/质量/定位/价值/推荐理由里 ≥6 字的接口或用途描述）、能力面不重复、非部署组件弱连通且无环、至少一个上游与一个下游。报告按能力面 rank 排序输出表格（输入/输出/上下游/接入方式）。
Alternatives：只要求“写出数据流文本”无法自动判定；要求“Hamiltonian 路径”会把 `memory → rag → agent` 这类分支结构误杀。

**2. 评分拆成技术组合成熟度与需求证据强度，两者不合并**
技术分沿用供给侧分项并重新配权（可靠度 40 / 供给 20 / 风险敞口 20 / 许可证 10 / 完整度 10）；需求分由 `plan_evidence()` 产出（等级 40 / 用户明确表态 25 / 独立来源 20 / 新鲜度 15），等级来自四级证据阶梯：用户反馈（`feedback.jsonl` 中 `source=user` 且点名组件）> 源报告接口依据（项目方自述）> 能力面推导的客户问题（待验证假设）> 无。
Alternatives：保留单一分数再加“证据提示”无法阻止虚高分被当成结论；引入规模/市场份额估算需要外部数据，本仓库没有来源。

**3. 判断用确定性阶梯，且“暂不建议”不进列表**
需求等级为无证据 → 暂不建议；风险敞口 ≤5/20（高风险组件 ≥75%）→ 暂不建议；需求分 ≥60 → 值得用户访谈；技术分 ≥80 → 值得技术试验；否则继续观察。被剔为“暂不建议”的候选只在 `## 今日结论` 计数并给出理由。
Alternatives：允许“暂不建议”出现在列表里会重新引入凑数动机。

**4. 冷却按 family 的最近一次出现日期计算，提前重现需要新增量**
`load_family_history()` 扫描运行日期前 14 天内的报告，记录最近出现日期、历史组件集合、历史证据等级与业务三元组。`cooldown_decision()`：<7 天无条件跳过；7–13 天只有出现新组件、证据等级提升或客户问题/预期结果变化才允许提前重现（并把理由写进今日结论）；≥14 天自然重新合格。
Alternatives：沿用“连续两天”规则无法阻止隔天复现；按标题或组件集合去重会漏掉同一方向的改写。

**5. 证据等级与禁用措辞在生成侧强制**
模板市场文案改写为带【待验证假设】/【已确认事实】标记的句子；`FORBIDDEN_CLAIMS` + `sanitize_claims()` 在渲染时清洗非法断言（含 LLM 增强段落），测试同时校验模板常量与渲染结果。
Alternatives：只在 KUN-TASK.md 里写“不要夸大”没有可验证的落点。

**6. 报告结构重排、删除低价值章节**
删除“单点项目机会”与笼统“行动建议”，改为报告级 `## 今日结论`（方案数、判断分布、冷却/暂不建议/门槛未过计数、原则）+ 方案级固定顺序。历史报告继续用旧解析路径渲染（`removeSummaryFields` 仍包含旧标签，`sectionText` 找不到新章节时为空）。

**7. 网页摘要字段改为方案判断 / 目标客户 / 需求证据**
`src/lib/feasibility.ts` 新增 `ScoreSummary` 与 `judgment` / `judgmentReason` / `evidenceLevel` / `techScore` / `demandScore` 解析，保留 `score` / `grade` / `scoreParts` 作为历史格式回退；视图用 `.feasibility-judgment` 与 `.feasibility-scores` 呈现，窄屏降为单列。

## Risks / Trade-offs

- 门槛变严后单日产出的方案数量会明显下降，甚至为 0：这是设计目标，需在 KUN-TASK.md 与汇报话术里说明“0 个是合法结果”。
- 需求证据强度天然偏低（系统内没有客户数据）：可能触发“需求分永远不到 60 → 永远不值得用户访谈”。缓解：`feedback.jsonl` 中 `source=user` 的记录是可积累的“已确认事实”来源，下一步动作明确要求把访谈结论写回该文件。
- 能力面交接表是人工整理的：新增能力面或新增模板时必须同步维护，测试用“每个模板都必须形成连通数据流”守住这一点。
- 网页摘要不再展示“业务定位”：定位句仍保留在正文与 `positioning` 字段，避免与“方案判断”重复占位。

## Migration Plan

1. 先改脚本与 Python 测试（生成侧新口径），用历史日期在临时数据根上生成样本对照。
2. 同步 `KUN-TASK.md` 与 Kun 定时任务入口提示，使生成后命名与核对步骤引用新字段。
3. 再改构建侧解析与视图，保持历史报告按旧格式渲染。
4. 回滚方式：脚本与任务规则一并回退即可，历史报告文件未被改写。
