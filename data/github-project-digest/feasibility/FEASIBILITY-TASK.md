# 每日 GitHub 项目组合可行性方案

> 触发方式：每天 06:30（Asia/Shanghai）。工作区：`/Users/elvis/Desktop/repo-signal`。
> 本文件是任务执行指令，由定时任务触发后交给 agent 按"执行步骤"完整执行，
> 并在结束时向用户汇报。
> 核心原则：**少而可信、能够验证**。当天没有合格方案是合法结果，
> 不要为了每日产出而生成逻辑松散、评分虚高的组合。

## 目标

以当天日报发现的 GitHub 项目为起点，结合最近 90 天项目池，每天产出 **0–3 个
多项目组合**，优先组成 **1 个成熟方向 + 1–2 个探索方向**：
- 成熟方向（mature）：固定模板命中的方向，组件供给已在池内核对；
- 探索方向（exploratory）：以今日可执行项目决定方向，从最近 90 天项目池补齐
  主数据流，标注待验证（组件可拼装 ≠ 市场需求成立）。

没有合格方向时允许少于 3 个，**0 个时如实报告"本轮无合格方案"**，不补位。

每个组合必须写清：**业务名标题 / 项目成员 / 数据流链条 / 逐步输入输出表 /
为什么是这几个 / 怎么连 / 接口信号 / 位置是否对口 / 要注意的地方 / 组件新鲜度 /
判断**，不写代码。组合里每个组件的角色名取它所在的**能力面**（安全扫描 / 代码理解 /
任务编排 / 隔离执行 / 评测观测 / 模型网关 / 长期记忆 / 检索增强 / 文档处理 /
本地运行 / 消息入口 / 设计约束），不是项目自己的最高分能力面。

**不做市场结论**：不写目标客户、市场机会、需求证据、差异化、付费意愿与市场规模；
这些既没有来源也没有必要。报告不含方案身份/业务语义等机器元数据；
`plan_family` / `variant` / 组件集合与证据状态记录在
`feasibility/plan-history.jsonl`，供跨日冷却。
两个评分只作参考，互不合并，出现在每个组合末尾的"判断"行与 `## 结论` 里：

- **技术组合成熟度**（0-100）= 组件可靠度 40 · 组件供给 20 · 风险敞口 20 · 许可证 10 · 完整度 10；
- **需求证据强度**（0-100）= 证据等级 40 · 用户明确表态 25 · 独立来源 20 · 新鲜度 15。

组件成熟不等于商业可行：需求侧没有可引用证据时，技术分再高也不能当成可行性结论。
方案判断只有四档：

| 判断 | 含义 |
|---|---|
| 值得用户访谈 | 需求侧已有可引用证据（等级 ≥ 项目方自述且强度 ≥60），先去访谈 |
| 值得技术试验 | 技术组合成熟度 ≥80，需求侧证据不足，只做技术试验 |
| 继续观察 | 两项都未到推进线，先补证据（含冷却中重现的方向） |
| 暂不建议 | 需求侧无任何可引用证据，或高风险组件占比 ≥75%；**不列入组合列表**，只在今日结论里计数说明 |

## 输入

- 项目池：`data/github-project-digest/daily/*.md` 与 `weekly/*.md` 中最近 90 天的全部项目
- 今日锚点：`data/github-project-digest/daily/<今天日期>.md`；当天无日报（周末/未生成）时不执行本任务，跳过并如实回报，不生成替代报告
- 需求证据：`data/github-project-digest/feedback.jsonl`（`source=user` 的条目是唯一"已确认事实"来源；其余需求表述最高只能标到"项目方自述"）
- 探索方向额外要求：每个方向至少 1 个今日可执行锚点，另从今日日报或最近 90 天
  项目池选择至少 2 个互补组件；今日锚点必须参与主数据流并决定客户问题（主面须
  明确胜出：最高面分 ≥2 且严格高于次高；部署形态定位或主面并列/低分的项目不能
  作锚点；互补组件须在对应能力面得分达标）。没有可连接的互补组件时，本轮只产出
  成熟方向

## 执行步骤

1. 校验输入：`python3 scripts/opportunity_analysis.py --check`
   - 期望输出形如 `POOL date=... anchor=... today=N unique=M ...`；
     若失败或 `daily/`、`weekly/` 无数据，检查目录后回报，不要猜测、
     不要联网核验 GitHub。
   - 若提示"当天日报缺失"（退出码 2，即当天日报文件不存在）：本次不执行
     可行性方案，向用户简短回报"今日无日报，已跳过"后结束。
2. 生成报告：`python3 scripts/opportunity_analysis.py`
   - 默认按今天日期输出到 `data/github-project-digest/feasibility/<今天>.md`
   - 脚本要求当天日报存在；缺失时以退出码 2 结束，不写报告、不追加
     runs.log，不回退到更早的日报；
   - 如需补跑历史日期：`--date YYYY-MM-DD`
   - 双轨产出：最多 1 个成熟方向 + 最多 2 个探索方向，总数 0–3 个。成熟方向由
     固定模板命中，先定业务方向再分配组件（优先避开已被其他方向占用的仓库）；
     探索方向以 1 个今日可执行项目为方向锚点（须参与主数据流），从今日项目或
     最近 90 天项目池选择 ≥2 个互补组件；历史组件只补齐数据流，不得改变锚点
     决定的客户问题，并标注待验证。
     没有合格方向时少于 3 个（甚至 0 个）是正常结果，不要为了凑数放宽标准。
   - 组合闭环门槛：每个方案必须给出可连接的组件数据流（起点 → 处理 → 终点）、
     每个组件的输入输出与接入方式；组件少于 3 个、缺接口依据（"仅标签相关"）、
     能力面重复、数据流不连通，或包含 Awesome List、资源索引、教程、纯内容等
     非执行组件的组合都由脚本剔除，只在今日结论里计数说明。
   - 方案身份：`plan_family` 由业务语义（customer + problem + expected_outcome）
     派生，与标题措辞、技术词、组件集合无关；成熟方向沿用模板 slug。`variant`
     仍由组件集合派生。仅换标题、换项目或换技术词不会产生新的业务方向。
   - 跨日去重（对所有运行生效，含补跑历史日期）：同一 `plan_family` **冷却 7–14 天**
     （`COOLDOWN_MIN_DAYS`–`COOLDOWN_DAYS`）。冷却期内无条件跳过；冷却中段
     （7–13 天）只有在**新增关键组件或证据等级提升**时才允许提前
     重现，报告会在"今日结论 → 冷却与重现"里说明理由。依据是 `feasibility/plan-history.jsonl`
     中运行日期之前的记录，同一文件集下结果可复现。
3. 审核优化组合标题（生成后，逐组合；标准见下节"命名标准"）：
   - 生成器已给出业务名（成熟方向用模板业务名、探索方向按客户问题派生）。
     再逐条读一遍：**读起来是不是一个业务名**（"给谁、解决什么"），而不是
     能力面拼接名（如 `可观测 · 代码智能平台`）或技术词堆叠。
   - 只改标题名称，以及正文里同一名称的引用（`## 结论` 列表里的名称）；
     其余内容一律不动——项目成员、数据流链条、输入输出表、怎么连、接口信号、
     位置是否对口、要注意的地方、组件新鲜度、判断行。
   - 硬约束：`plan_family` / `variant` 保持原样（跨日冷却、周报选择器都依赖它）；
     改后的名称必须仍指向同一个客户问题（`plan-history.jsonl` 里的 `family` 不变）。
   - 原名已经清楚时不要为了改而改；确实改了名称，就在报告简介（`## 可行性方案`
     之前）补一行：`> 命名：标题由生成后命名步骤优化，方案身份 plan_family 未变。`
4. 核对产出：读取报告，确认
   - 组合小节数量在 **0–3 个**之间（0 个时必须写明"本轮无合格方案"）；
     成熟方向 ≤1 个、探索方向 ≤2 个；
   - 每个组合的标题是**业务名**（不是项目名、不是能力面拼接名、不含 `·` 分段），
     下面紧跟 `**项目**：` 一行列出成员仓库；
   - 每个组合有数据流链条（`> N 个项目串成一条链：角色 → 角色 → …`）与
     `| 角色 | 项目 | 这一步做什么（输入 → 输出） |` 表；表行数与组件数一致，
     行顺序就是数据流顺序（上一步的输出＝下一步的输入）；
   - 每个组合有六项据实说明：`**为什么是这几个**`、`**怎么连**`、`**接口信号`、
     `**位置可能不对口**`（没有错配时不出现，属正常）、`**要注意的地方`、
     `**组件新鲜度**`，以及最后的 `**判断**` 行；
   - 每个组合至少 1 个组件来自今日日报，并在表中标注"今日发现"；
   - `**要注意的地方` 逐组件一行、只取源报告风险描述的首句；
   - 报告不含目标客户、市场机会、需求证据、差异化、MVP 实验、最大不确定性、
     下一步动作等段落，也不含"刚需 / 愿意付费 / 市场已验证"等无来源结论；
   - `**判断**` 行的取值属于四档（值得用户访谈 / 值得技术试验 / 继续观察 /
     暂不建议），且列表里不出现"暂不建议"的组合；行内的技术分与需求分须与
     `## 结论` 一致，各自等于分项之和；
   - `## 结论` 在最后一个组合之后，逐组合给出业务名、项目数、两个分数与判断，
     并说明两个分数互不合并；
   - 报告不含方案身份/业务语义等机器元数据（`plan_family` / `variant`
     记录在 `feasibility/plan-history.jsonl`）；
   - 报告说明（`## 今日结论` 之前的引用行，含命名说明行）保持 150 字以内：
     只说明生成方式、输入锚点、组合数量与待验证提示；不展开阅读顺序、闭环门槛、
     评分定义、冷却与验证路径等内部规则；
   - `## 今日结论` 在第 1 个组合之前，并写明判断分布、被冷却跳过/暂不建议/
     闭环门槛未过的候选及其原因；
   - runs.log（`data/github-project-digest/feasibility/runs.log`）追加了本次记录
     （含 `mature=` / `exploratory=` / `judgments=` 等计数）；
   - 脚本退出码为 0；
   - 组合业务名符合命名标准（8–20 字、无 `·` 等标点分段、同报告内不重名）；
   - 改名不改变方案身份：`plan_family` / `variant` 以 `feasibility/plan-history.jsonl`
     的本次记录为准；
   - 若报告写明"本轮无合格方案"：这是合法结果，按第 5 步如实汇报，不要补写组合，
     也不要把空报告当成正常的组合产出。
5. 向用户汇报（简短）：
   - 本轮组合数量与轨道分布（如"1 个成熟方向 + 1 个探索方向"，或"本轮无合格方案"）；
   - 每个组合的业务名、组件项目（今日发现 + 从池中补齐的）与数据流链条；
   - 每个组合的判断、技术组合成熟度与需求证据强度（N/100）；
   - 值得注意的信号：接口信号、位置可能不对口、超过 30 天未更新的组件；
   - 若改了标题：列出改前 → 改后；若未改，说明保留原名；
   - 报告完整路径 `data/github-project-digest/feasibility/<今天>.md`；
   - 若为"本轮无合格方案"：说明候选数量与原因（技术分未达线 / 暂不建议 /
     冷却跳过 / 缺少今日锚点），不补组合；
   - 如失败：说明失败原因与已检查的输入状态，最多重试一次，不要重复运行。

## 命名标准（生成后审核优化）

标题是**组合的业务名**，不是项目名、不是能力面拼接名。生成器已按客户问题派生
（如客户问题"模型与供应商多，接入方式和花费不可控" → `多模型接入治理平台`；
成熟方向用模板业务名），生成后再逐条审核一遍：

1. 读起来要像一个业务名：回答"这套组合给谁、解决什么"，例如 `Agent 任务编排平台`、
   `可溯源知识检索助手`、`改动与依赖安全复核平台`；
2. 不堆技术词：能力面词最多留 1 个做定位；带 `·` 的段式名（如
   `可观测 · 代码智能平台`）必须改成连续中文；
3. 长度 8–20 个汉字（可含 1–2 个英文词，如 Agent / RAG），不加副标题、括号说明
   或标点分段；标题只保留名称，项目成员放在标题下的 `**项目**：` 一行；
4. 同一份报告内名称不重复；成熟方向本来就是业务名，只在明显更好时微调
   （例如去掉过长的括号补充），不重新发明方向；
5. 不夸大、不承诺：不得出现"首选 / 最佳 / 领先 / 唯一 / 刚需 / 愿意付费"；
6. 改名的目的是更清楚，不是更好听：含义不变优先于措辞新颖；拿不准就保留原名。

## 产出

- `data/github-project-digest/feasibility/YYYY-MM-DD.md`：组合报告（0–3 个组合：
  成熟 ≤1 + 探索 ≤2；0 个时必须写明"本轮无合格方案"；标题已按命名标准审核）
- `data/github-project-digest/feasibility/plan-history.jsonl`：方案身份记录
  （脚本自动维护；跨日冷却的输入；`plan_family` 保持不变；空值字段省略）
- `data/github-project-digest/feasibility/runs.log`：运行记录（锚点、池规模、
  组合数、轨道计数、冷却/暂不建议/门槛未过计数与判断分布）

## 验证标准

- 脚本退出码 0；
- 组合数在 0–3 个之间（0 个时必须写明"本轮无合格方案"），其中成熟方向 ≤1、探索方向 ≤2；
- 每个组合的标题是业务名（8–20 字、无 `·` 分段、同报告内不重名），并紧跟 `**项目**：` 成员行；
- 每个组合含 ≥1 个今日发现项目并标注"今日发现"，且通过闭环门槛（组件 ≥3、
  有接口依据、能力面不重复、数据流连通）；探索方向的锚点在主数据流中
  （部署形态面不算）、主面明确胜出，其余组件可来自项目池；
- 每个组合有：数据流链条、`| 角色 | 项目 | 这一步做什么（输入 → 输出） |` 表
  （行序＝数据流顺序）、`**为什么是这几个**`、`**怎么连**`、`**接口信号`、
  `**要注意的地方`（逐组件首句）、`**组件新鲜度**`、`**判断**`；
- 角色名取该步骤所在的能力面（安全扫描 / 代码理解 / 任务编排 / 隔离执行 /
  评测观测 / 模型网关 / 长期记忆 / 检索增强 / 文档处理 / 本地运行 / 消息入口 /
  设计约束），不是项目自己的最高分能力面；
- `**判断**` 属于四档之一；技术组合成熟度与需求证据强度分别给出 N/100，
  各自总分＝分项之和、与 `## 结论` 一致；两个分数不合并；
- 正文不含目标客户、市场机会、需求证据、差异化、MVP 实验、最大不确定性、
  下一步动作等段落，也不含"刚需 / 愿意付费 / 市场已验证"等无来源断言；
- `plan-history.jsonl` 已追加本次记录（含 plan_family / variant / 组件集合与证据状态）；
- 冷却（7–14 天）与暂不建议的组合不出现在组合列表中，只在 `## 今日结论` 里说明；
- 组件全部来自项目池（不引用池外项目）。

## 规则与边界

- 本任务只读取仓库内已有报告，不联网核验 GitHub；所有项目事实以日报/周报为准。
- 报告是可行性研究草稿，不包含代码，不构成商业结论；需求侧结论必须带证据等级。
- 只读 `daily/`、`weekly/` 下的源报告；只写 `feasibility/` 目录；不修改脚本。
- 可选增强：环境变量 `OPPORTUNITY_LLM_API_KEY`（或 `OPENAI_API_KEY`，
  可配 `OPPORTUNITY_LLM_BASE_URL` / `OPPORTUNITY_LLM_MODEL`）时，
  脚本自动在报告尾部附 LLM 增强视角；失败不影响主流程。

python3 scripts/opportunity_analysis.py --check   # 只校验输入（当天无日报时退出码 2）
