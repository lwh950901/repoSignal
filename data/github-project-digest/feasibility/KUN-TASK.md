# Kun 定时任务：每日 GitHub 项目组合可行性方案

> 触发方式：每天 06:30（Asia/Shanghai）。工作区：`/Users/elvis/Desktop/repo-signal`。
> 本文件是任务执行指令，Kun 定时触发后由 agent 按"执行步骤"完整执行，
> 并在结束时向用户汇报。
> 核心原则：**少而可信、能够验证**。当天没有合格方案是合法结果，
> 不要为了每日产出而生成逻辑松散、评分虚高的组合。

## 目标

以当天日报发现的 GitHub 项目为锚点，结合最近 90 天项目池，每天产出 **0–3 个
"多 GitHub 项目组合"可行性方案**，优先组成 **1 个成熟方向 + 1–2 个探索方向**：
- 成熟方向（mature）：固定模板命中的业务方向，组件供给已在池内核对；
- 探索方向（exploratory）：以今日可执行项目决定方向，从最近 90 天项目池补齐
  主数据流，标注待验证（组件可拼装 ≠ 市场需求成立）。

没有合格方向时允许少于 3 个，**0 个时如实报告"本轮无合格方案"**，不补位。

每个方案必须写清：**方案判断 / 业务定位 / 业务轨道 / 业务语义 / 目标客户 / 市场机会 /
需求证据（一行：等级与要点）/ 组合依据 / 组合方案（角色 / 项目 / 入选理由）/ 差异化 /
双评分 / 可证伪的 MVP 实验 / 下一步动作（仅 1 条）/ 风险（逐组件一句、不带括注）**，不写代码。客户问题、接入方式、
组件数据流（输入输出与上下游）与最大不确定性只作内部校验，不出现在正文。
两个评分互不合并：

- **技术组合成熟度**（0-100）= 组件可靠度 40 · 组件供给 20 · 风险敞口 20 · 许可证 10 · 完整度 10；
- **需求证据强度**（0-100）= 证据等级 40 · 用户明确表态 25 · 独立来源 20 · 新鲜度 15。

组件成熟不等于商业可行：需求侧没有可引用证据时，技术分再高也不能当成可行性结论。
方案判断只有四档，取代旧的"优先推进最高分方案"：

| 判断 | 含义 |
|---|---|
| 值得用户访谈 | 需求侧已有可引用证据（等级 ≥ 项目方自述且强度 ≥60），先去访谈 |
| 值得技术试验 | 技术组合成熟度 ≥80，需求侧证据不足，只做技术试验 |
| 继续观察 | 两项都未到推进线，先补证据（含冷却中重现的方向） |
| 暂不建议 | 需求侧无任何可引用证据，或高风险组件占比 ≥75%；**不列入方案列表**，只在今日结论里计数说明 |

## 输入

- 项目池：`data/github-project-digest/daily/*.md` 与 `weekly/*.md` 中最近 90 天的全部项目
- 今日锚点：`data/github-project-digest/daily/<今天日期>.md`；当天无日报（周末/未生成）时不执行本任务，跳过并如实回报，不生成替代报告
- 需求证据：`data/github-project-digest/feedback.jsonl`（`source=user` 的条目是唯一"已确认事实"来源；其余需求表述最高只能标到"项目方自述"）
- 探索方向额外要求：每个方向至少 1 个今日可执行锚点，另从今日日报或最近 90 天
  项目池选择至少 2 个互补组件；今日锚点必须参与主数据流（只有部署形态定位的项目
  不能作锚点）并决定客户问题。没有可连接的互补组件时，本轮只产出成熟方向

## 执行步骤

1. 校验输入：`python3 scripts/opportunity_analysis.py --check`
   - 期望输出形如 `POOL date=... anchor=... today=N unique=M ...`；
     若失败或 `daily/`、`weekly/` 无数据，检查目录后回报，不要猜测、
     不要联网核验 GitHub。
   - 若提示"当天日报缺失"（退出码 2，即当天日报文件不存在）：本次不执行
     可行性方案，向用户简短回报"今日无日报，已跳过"后结束。
2. 生成报告：`python3 scripts/opportunity_analysis.py`
   - 默认按今天日期输出到 `data/github-project-digest/feasibility/<今天>.md`
   - 脚本要求当天日报存在；缺失时以退出码 2 结束，不写报告、不追加
     runs.log，不回退到更早的日报；
   - 如需补跑历史日期：`--date YYYY-MM-DD`
   - 双轨产出：最多 1 个成熟方向 + 最多 2 个探索方向，总数 0–3 个。成熟方向由
     固定模板命中，先定业务方向再分配组件（优先避开已被其他方向占用的仓库）；
     探索方向以 1 个今日可执行项目为方向锚点（须参与主数据流），从今日项目或
     最近 90 天项目池选择 ≥2 个互补组件；历史组件只补齐数据流，不得改变锚点
     决定的客户问题，并标注待验证。
     没有合格方向时少于 3 个（甚至 0 个）是正常结果，不要为了凑数放宽标准。
   - 组合闭环门槛：每个方案必须给出可连接的组件数据流（起点 → 处理 → 终点）、
     每个组件的输入输出与接入方式；组件少于 3 个、缺接口依据（"仅标签相关"）、
     能力面重复、数据流不连通，或包含 Awesome List、资源索引、教程、纯内容等
     非执行组件的组合都由脚本剔除，只在今日结论里计数说明。
   - 方案身份：`plan_family` 由业务语义（customer + problem + expected_outcome）
     派生，与标题措辞、技术词、组件集合无关；成熟方向沿用模板 slug。`variant`
     仍由组件集合派生。仅换标题、换项目或换技术词不会产生新的业务方向。
   - 跨日去重（对所有运行生效，含补跑历史日期）：同一 `plan_family` **冷却 7–14 天**
     （`COOLDOWN_MIN_DAYS`–`COOLDOWN_DAYS`）。冷却期内无条件跳过；冷却中段
     （7–13 天）只有在**新增关键组件、证据等级提升或客户问题变化**时才允许提前
     重现，报告会在"今日结论 → 冷却与重现"里说明理由。依据是运行日期之前
     已存在的报告文件，同一文件集下结果可复现。
3. 优化方案名称（生成后，逐方案；标准见下节"命名标准"）：
   - 只改展示名与标题格式：`### N.` 标题统一为 `### N. 名称`；
     `**业务定位**` 里以引号引用的同一名称（如有）一并同步；其余内容一律不动——
     `**方案判断**`、`**方案身份**`（plan_family / variant）、`**业务语义**`、
     `**业务轨道**`、`**市场机会**`、`**需求证据**`、`**组合依据**`、
     `**双评分**`、`**MVP 实验**`、`**下一步动作**`、组合表、风险。
   - 硬约束：`plan_family` / `variant` 保持原样（跨日冷却、周报选择器都依赖它）；
     改后的名称必须仍指向同一个客户 + 客户问题 + 预期结果。
   - 原名称已经清楚时不要为了改而改；确实改了名称，就在报告简介（`## 可行性方案`
     之前）补一行：`> 命名：标题由生成后命名步骤优化，方案身份 plan_family 未变。`
4. 核对产出：读取报告，确认
   - 方案小节数量在 **0–3 个**之间（0 个时必须写明"本轮无合格方案"）；
     成熟方向 ≤1 个、探索方向 ≤2 个；
   - 每个方案有 `**方案判断**：` 行，取值属于四档（值得用户访谈 / 值得技术试验 /
     继续观察 / 暂不建议），且报告列表里不出现"暂不建议"的方案；
   - 每个方案有 `**市场机会**`、`**需求证据**`（一行）、`**组合依据**`、
     `**组合方案**` 表（角色 / 项目 / 入选理由）、`**双评分**`、`**MVP 实验**`
     （测试场景 / 测试数据 / 周期 / 成功指标 / 失败指标 / 停止条件）、
     `**下一步动作**`（只保留 1 条）、`**主要风险（来源报告）**`（逐组件一句、
     不带括注）；正文不含客户问题、接入方式、组件数据流与最大不确定性段落；
   - 需求与市场表述按证据等级标注（已确认事实 / 项目方自述 / 待验证假设 /
     无证据），不出现"刚需、愿意付费、市场已验证"等无来源结论；
   - 每个方案组合表（角色 / 项目 / 入选理由）里至少 1 个项目来自今日日报；
   - 每个方案含 `**业务轨道**` 与 `**业务语义**` 行（track / customer / problem /
     workflow / delivery / expected_outcome / evidence_status）；
   - 报告说明（`## 今日结论` 之前的引用行，含命名说明行）保持 150 字以内：只说明
     生成方式、输入锚点、方向数量与待验证／复核提示；不展开阅读顺序、闭环门槛、
     评分定义、冷却与验证路径等内部规则；
   - `## 今日结论` 在第 1 个方案之前，并写明判断分布、被冷却跳过/暂不建议/
     闭环门槛未过的候选及其原因；
   - runs.log（`data/github-project-digest/feasibility/runs.log`）追加了本次记录
     （含 `mature=` / `exploratory=` / `judgments=` 等计数）；
   - 脚本退出码为 0；
   - 每个方案的名称符合命名标准（8–20 字、无 `·` 等标点分段、同报告内不重名），
     并与 `**业务语义**` 的客户/问题/预期结果一致；
   - `**方案身份**` 行未被改动（plan_family / variant 与脚本生成时一致）；
   - 若报告写明"本轮无合格方案"：这是合法结果，按第 5 步如实汇报，不要补写方案，
     也不要把空报告当成正常的组合产出。
5. 向用户汇报（简短）：
   - 本轮方案数量与轨道分布（如"1 个成熟方向 + 1 个探索方向"，或"本轮无合格方案"）；
   - 每个方案的名称、轨道、判断与核心组合：今日锚点项目（角色）+ 关键补充组件；
   - 每个方案的双评分（技术组合成熟度 N/100、需求证据强度 N/100 与档位）；
   - 每个方案 MVP 实验的周期与停止条件（一句话即可，不必复述全部指标）；
   - 若改了名称：列出改前 → 改后；若未改，说明保留原名；
   - 报告完整路径 `data/github-project-digest/feasibility/<今天>.md`；
   - 若为"本轮无合格方案"：说明候选数量与原因（技术分未达线 / 暂不建议 /
     冷却跳过 / 缺少今日锚点），不补方案；
   - 如失败：说明失败原因与已检查的输入状态，最多重试一次，不要重复运行。

## 命名标准（生成后优化）

生成器给的名称是“能力面拼装名”（如 `本地优先 · 知识增强 · Agent 工作台`），只保证
可复现，不一定好读；生成后按下面顺序优化成业务名：

1. 优先回答“给谁、解决什么、做成什么样”，例如 `企业私有化知识助手`、
   `可溯源的本地知识助手`、`供应链合规扫描`；
2. 用业务词而非技术词堆叠：能力面词最多留 1 个做定位，带 `·` 的段式名改成连续中文；
3. 长度 8–20 个汉字（可含 1–2 个英文词，如 Agent / RAG），不加副标题、括号说明
   或标点分段；标题只保留名称；
4. 同一份报告内名称不重复；成熟方向本来就是业务名，只在明显更好时微调
   （例如去掉过长的括号补充），不重新发明方向；
5. 不夸大、不承诺：不得出现“首选 / 最佳 / 领先 / 唯一”，探索方向不得写成已验证结论；
6. 改名的目的是更清楚，不是更好听：含义不变优先于措辞新颖；拿不准就保留原名。

## 产出

- `data/github-project-digest/feasibility/YYYY-MM-DD.md`：可行性方案报告（0–3 个方案：
  成熟 ≤1 + 探索 ≤2；0 个时必须写明"本轮无合格方案"；展示名称已按命名标准优化，
  方案身份 plan_family 保持不变）
- `data/github-project-digest/feasibility/runs.log`：运行记录（锚点、池规模、
  组合数、轨道计数、冷却/暂不建议/门槛未过计数与判断分布）

## 验证标准

- 脚本退出码 0；
- 方案数在 0–3 个之间（0 个时必须写明"本轮无合格方案"），其中成熟方向 ≤1、探索方向 ≤2；
- 每个方案含 ≥1 个今日锚点项目，且通过闭环门槛（组件 ≥3、有接口依据、能力面不重复、数据流连通）；
  探索方向的锚点在主数据流中（部署形态面不算）并决定客户问题，其余组件可来自项目池；
- 每个方案有 `**业务轨道**`、`**业务语义**`、`**方案判断**`（四档之一）行；
- 组件数据流（每个组件的输入/输出/上下游）与接入方式仅作内部校验，正文不展开；
- 每个方案有 `**双评分**` 行：技术组合成熟度与需求证据强度分别给出 N/100（含分项明细，各自总分=分项之和）；
- 每个方案有可证伪的 `**MVP 实验**`：测试场景 / 测试数据 / 周期 / 成功指标 / 失败指标 / 停止条件六项齐全；
- 需求与市场表述按证据等级标注，且不含"刚需 / 愿意付费 / 市场已验证"等无来源断言；
- 方案名称符合命名标准（8–20 字、无 `·` 等标点分段、同报告内不重名）且 `**方案身份**` 行保持脚本生成时的值；
- 冷却（7–14 天）与暂不建议的方案不出现在方案列表中，只在 `## 今日结论` 里说明；
- 组件全部来自项目池（不引用池外项目）。

## 规则与边界

- 本任务只读取仓库内已有报告，不联网核验 GitHub；所有项目事实以日报/周报为准。
- 报告是可行性研究草稿，不包含代码，不构成商业结论；需求侧结论必须带证据等级。
- 只读 `daily/`、`weekly/` 下的源报告；只写 `feasibility/` 目录；不修改脚本。
- 可选增强：环境变量 `OPPORTUNITY_LLM_API_KEY`（或 `OPENAI_API_KEY`，
  可配 `OPPORTUNITY_LLM_BASE_URL` / `OPPORTUNITY_LLM_MODEL`）时，
  脚本自动在报告尾部附 LLM 增强视角；失败不影响主流程。

## 手动运行

```bash
python3 scripts/opportunity_analysis.py --check   # 只校验输入（当天无日报时退出码 2）
python3 scripts/opportunity_analysis.py           # 生成今天报告
```
