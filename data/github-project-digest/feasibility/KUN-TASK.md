# Kun 定时任务：每日 GitHub 项目组合可行性方案

> 触发方式：每天 06:30（Asia/Shanghai）。工作区：`/Users/elvis/Desktop/repo-signal`。
> 本文件是任务执行指令，Kun 定时触发后由 agent 按"执行步骤"完整执行，
> 并在结束时向用户汇报。

## 目标

以当天日报发现的 GitHub 项目为锚点，结合最近 90 天项目池，每天产出 **1–3 个"多
GitHub 项目组合"可行性方案**，优先组成 **1 个成熟方向 + 1–2 个探索方向**：
- 成熟方向（mature）：固定模板命中的业务方向，组件供给已在池内核对；
- 探索方向（exploratory）：用今日新发现直接拼接的方向，标注待验证（组件可拼装
  ≠ 市场需求成立）。
没有合格探索方向时允许少于 3 个，不强行补齐；一个都没拼出来时如实报告
"无合格方案"。每个方案含业务定位 / 目标客户 / 市场机会 / 组合分工 / 差异化 /
MVP 范围 / 风险 / 业务语义（customer / problem / workflow / delivery /
expected_outcome）/ 0-100 综合评分，不写代码。
验证路径为固定文案，统一放在报告简介。

## 输入

- 项目池：`data/github-project-digest/daily/*.md` 与 `weekly/*.md` 中最近 90 天的全部项目
- 今日锚点：`data/github-project-digest/daily/<今天日期>.md`；当天无日报（周末/未生成）时不执行本任务，跳过并如实回报，不生成替代报告
- 探索方向额外要求：今日锚点 ≥3 个项目（1 个锚点 + ≥2 个互补组件），否则本轮只产出成熟方向

## 执行步骤

1. 校验输入：`python3 scripts/opportunity_analysis.py --check`
   - 期望输出形如 `POOL date=... anchor=... today=N unique=M ...`；
     若失败或 `daily/`、`weekly/` 无数据，检查目录后回报，不要猜测、
     不要联网核验 GitHub。
   - 若提示"当天日报缺失"（退出码 2，即当天日报文件不存在）：本次不执行
     可行性方案，向用户简短回报"今日无日报，已跳过"后结束。
2. 生成报告：`python3 scripts/opportunity_analysis.py`
   - 默认按今天日期输出到 `data/github-project-digest/feasibility/<今天>.md`
   - 脚本要求当天日报存在；缺失时以退出码 2 结束，不写报告、不追加
     runs.log，不回退到更早的日报；
   - 如需补跑历史日期：`--date YYYY-MM-DD`
   - 双轨产出：最多 1 个成熟方向 + 最多 2 个探索方向，总数 1–3 个。成熟方向由
     固定模板命中，先定业务方向再分配组件（优先避开已被其他方向占用的仓库）；
     探索方向由今日锚点拼接（≥1 个今日锚点 + ≥2 个互补组件）并标注待验证。
     没有合格探索方向时少于 3 个是正常结果，不要为了凑满 3 个而放宽标准。
   - 方案身份：`plan_family` 由业务语义（customer + problem + expected_outcome）
     派生，与标题措辞、技术词、组件集合无关；成熟方向沿用模板 slug。`variant`
     仍由组件集合派生。仅换标题、换项目或换技术词不会产生新的业务方向。
   - 新鲜度规则（对所有运行生效，含补跑历史日期）：同一方案（按 plan_family
     判定）最多连续出现两天；已连续出现两天的方案在第三天自动跳过，报告简介会注明。
     依据是运行日期之前已存在的报告文件，同一文件集下结果可复现。
3. 优化方案名称（生成后，逐方案；标准见下节“命名标准”）：
   - 只改展示名：`### N.` 标题里的名称部分、“## 行动建议”里引用的同一名称，以及
     `**业务定位**` 里以引号引用的同一名称（如有）；其余内容一律不动——
     `**方案身份**`（plan_family / variant）、`**业务语义**`、
     `**业务轨道**`、`**方案评分**`、组合表、业务定位/目标客户/市场机会/
     差异化/MVP/风险、单点项目机会、行动建议的其余条目。
   - 硬约束：`plan_family` / `variant` 保持原样（跨天去重、新鲜度规则与周报
     选择器都依赖它）；改后的名称必须仍指向同一个客户 + 客户问题 + 预期结果。
   - 原名称已经清楚时不要为了改而改；确实改了名称，就在报告简介（`## 可行性方案`
     之前）补一行：`> 命名：标题由生成后命名步骤优化，方案身份 plan_family 未变。`
4. 核对产出：读取报告，确认
   - 方案小节数量在 **1–3 个**之间（数据不足时允许少于 3 个，按实际数量核对）；
   - 每个方案有 `**业务轨道**：` 行，且成熟方向 ≤1 个、探索方向 ≤2 个；
   - 每个方案有 `**业务语义**：` 行（track / customer / problem / workflow /
     delivery / expected_outcome / evidence_status）；
   - 探索方向带 `**待验证说明**`，市场机会以"待验证假设"表述；
   - 每个方案组合表（角色 / 项目 / 入选理由）里至少 1 个项目来自今日日报；
   - 每个方案含 `**方案评分**：N/100` 行（含分项明细，总分=分项之和）；
   - runs.log（`data/github-project-digest/feasibility/runs.log`）追加了本次记录
     （含 `mature=` / `exploratory=` 计数）；
   - 脚本退出码为 0；
   - 每个方案的名称符合命名标准（8–20 字、无 `·` 等标点分段、同报告内不重名），
     并与 `**业务语义**` 的客户/问题/预期结果一致；
   - `**方案身份**` 行未被改动（plan_family / variant 与脚本生成时一致）；
   - 若报告写明"本轮无合格方案"：这是合法结果，按第 5 步如实汇报，不要补写方案，
     也不要把空报告当成正常的组合产出。
5. 向用户汇报（简短）：
   - 本轮方案数量与轨道分布（如"1 个成熟方向 + 2 个探索方向"）；
   - 每个方案的名称、轨道与核心组合：今日锚点项目（角色）+ 关键补充组件；
   - 每个方案的评分（N/100 与档位，如 76/100（中））；
   - 若改了名称：列出改前 → 改后；若未改，说明保留原名；
   - 报告完整路径 `data/github-project-digest/feasibility/<今天>.md`；
   - 若为"本轮无合格方案"：说明候选数量与原因（未达合格线 / 缺少今日锚点），不补方案；
   - 如失败：说明失败原因与已检查的输入状态，最多重试一次，不要重复运行。

## 命名标准（生成后优化）

生成器给的名称是“能力面拼装名”（如 `本地优先 · 知识增强 · Agent 工作台`），只保证
可复现，不一定好读；生成后按下面顺序优化成业务名：

1. 优先回答“给谁、解决什么、做成什么样”，例如 `企业私有化知识助手`、
   `可溯源的本地知识助手`、`供应链合规扫描`；
2. 用业务词而非技术词堆叠：能力面词最多留 1 个做定位，带 `·` 的段式名改成连续中文；
3. 长度 8–20 个汉字（可含 1–2 个英文词，如 Agent / RAG），不加副标题、括号说明
   或标点分段；
4. 同一份报告内名称不重复；成熟方向本来就是业务名，只在明显更好时微调
   （例如去掉过长的括号补充），不重新发明方向；
5. 不夸大、不承诺：不得出现“首选 / 最佳 / 领先 / 唯一”，探索方向不得写成已验证结论；
6. 改名的目的是更清楚，不是更好听：含义不变优先于措辞新颖；拿不准就保留原名。

## 产出

- `data/github-project-digest/feasibility/YYYY-MM-DD.md`：可行性方案报告（1–3 个方案：
  成熟 ≤1 + 探索 ≤2；允许少于 3 个；0 个时必须写明"本轮无合格方案"；
  展示名称已按命名标准优化，方案身份 plan_family 保持不变）
- `data/github-project-digest/feasibility/runs.log`：运行记录（锚点、池规模、组合数与轨道计数）

## 验证标准

- 脚本退出码 0；
- 方案数在 1–3 个之间（0 个时必须写明"本轮无合格方案"），其中成熟方向 ≤1、探索方向 ≤2；
- 每个方案含 ≥1 个今日锚点项目；
- 每个方案有 `**业务轨道**` 与 `**业务语义**` 行；探索方向必须有"待验证"标注；
- 方案名称符合命名标准（8–20 字、无 `·` 等标点分段、同报告内不重名）且
  `**方案身份**` 行保持脚本生成时的值；
- 每个方案有 0-100 综合评分行（组件可靠度/组件供给/风险敞口/今日锚点/来源多样性/许可证/完整度，含高中低档位）；
- 组件全部来自项目池（不引用池外项目）。

## 规则与边界

- 本任务只读取仓库内已有报告，不联网核验 GitHub；所有项目事实以日报/周报为准。
- 报告是可行性研究草稿，不包含代码，不构成商业结论。
- 只读 `daily/`、`weekly/` 下的源报告；只写 `feasibility/` 目录；不修改脚本。
- 可选增强：环境变量 `OPPORTUNITY_LLM_API_KEY`（或 `OPENAI_API_KEY`，
  可配 `OPPORTUNITY_LLM_BASE_URL` / `OPPORTUNITY_LLM_MODEL`）时，
  脚本自动在报告尾部附 LLM 增强视角；失败不影响主流程。

## 手动运行

```bash
python3 scripts/opportunity_analysis.py --check   # 只校验输入（当天无日报时退出码 2）
python3 scripts/opportunity_analysis.py           # 生成今天报告
```
