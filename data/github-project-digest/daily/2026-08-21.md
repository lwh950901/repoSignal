### 1. 爆发型：RyanCodrai/turbovec — 92/100

- 仓库：[RyanCodrai/turbovec](https://github.com/RyanCodrai/turbovec)
- 一句话定位：基于 TurboQuant 的 Rust 向量索引，提供 Python 绑定，面向低内存、低延迟和本地/隔离网络 RAG。
- 类型与适合用途：爆发型；适合想试验量化向量检索、构建本地 RAG 或研究 SIMD/持久化索引的开发者。
- 核心亮点与场景：GitHub Trending 2026-08-21 显示当日新增约 251 Stars；仓库当前实时快照为 15,898 Stars / 1,382 Forks，已超过爆发型 5,000 Stars 下限。它把在线增量索引、过滤检索、增量同步和本地部署组合到一个小型索引库中，适合做隐私敏感的文档检索或混合召回第二阶段。
- 主要技术栈：Rust、Python bindings、TurboQuant、SIMD（ARM NEON / x86 AVX）、NumPy、LangChain/LlamaIndex/Haystack/Agno 集成。
- 实时指标：15,898 Stars / 1,382 Forks；MIT；未归档；最近推送 2026-08-20；无正式 Release 标签（本轮未核实到）。
- 近期有意义活动：GitHub Trending 当日 +251 Stars；仓库页面显示约 362 次提交、benchmarks、docs、examples、CI 配置和 SECURITY.md，最近代码仍在更新。
- 质量证据：README 给出 `pip install turbovec`、Rust 构建和可运行示例；公开 benchmarks 对比 FAISS，并提供 recall、压缩、搜索速度、增删与持久化脚本；仓库包含 LICENSE、CHANGELOG、CONTRIBUTING、测试/CI 入口及跨平台 SIMD fallback 说明。
- 风险：项目较新，README 的性能结论主要来自作者提供的固定硬件/数据集基准；TurboQuant 量化会带来召回与数据分布风险，生产前应在自己的 embedding、维度、过滤比例和 CPU 上复测。
- 推荐理由：这是今天同时满足实时加速证据、质量门槛和可复现入口的候选；从 `pip install` 到 benchmark 都足够短，适合先做一个本地 RAG 小基准再决定是否替换现有向量库。

### 4. 学习型：agent-substrate/substrate — 90/100

- 仓库：[agent-substrate/substrate](https://github.com/agent-substrate/substrate)
- 一句话定位：基于 Kubernetes 的高密度 Agent runtime，通过 actor/worker 映射、挂起恢复和状态快照承载大规模有状态 Agent。
- 类型与适合用途：学习型；适合拆解 Agent 基础设施、调度控制面、gVisor/microVM 隔离、状态持久化和多租户资源复用，不以直接生产部署为首要目标。
- 核心亮点与场景：项目把“应用 actor 数量大于物理 worker 数量”的空闲复用假设落到控制面，实现 actor 创建/销毁、挂起/恢复、实时分配和请求路由；README 的 Counter Demo 展示约 250 个有状态 actor 在 8 个物理 Pod 上复用，适合研究长任务 Agent 的成本与恢复模型。
- 主要技术栈：Go、Kubernetes、OCI containers、gVisor、microVM、Pod autoscaling、状态快照与控制面调度。
- 实时指标：1,364 Stars / 251 Forks；Apache-2.0；未归档；最近推送 2026-08-20；Release v0.0.0。
- 近期有意义活动：仓库页面显示约 590 次提交、225 个 Issues、157 个 Pull requests；本轮实时页面看到 benchmarking、demos、docs、`.agents/skills`、CI 与 Go 模块等结构，近期代码仍在推进。
- 质量证据：README 明确给出 actor teleport、状态持久化和 30x+ oversubscription 的 Demo；提供 Counter Demo walkthrough、benchmarking 目录和多种 sandbox/worker 设计入口；仓库有 GOVERNANCE、COLLABORATING、CONTRIBUTING、LICENSE 与 SECURITY 相关文件。
- 风险：README 明确说明不是官方 Google 产品；v0.0.0、较高的 Issue/PR 数量和复杂的 Kubernetes/gVisor 依赖表明仍属早期基础设施。Demo 的复用比率和恢复延迟不能直接迁移到不同硬件/工作负载；不要照搬其调度假设、权限边界或快照策略到生产。
- 推荐理由：学习对象具体且可复现：先读 actor-worker 映射，再跑 Counter Demo，最后对照 benchmarking 观察恢复和复用代价；它比泛泛的 Agent SDK 更适合建立“Agent runtime 为什么这样设计”的系统视角。
