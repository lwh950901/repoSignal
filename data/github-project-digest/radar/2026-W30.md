# 开源雷达周刊

![开源雷达周刊｜每周开源项目精选](/covers/repository-radar-weekly-subtitle.png)

这一周的日报明显从“如何做一个 Agent”转向“如何让 Agent 真正运行起来”。浏览器调试、观测、成本归因、沙箱、知识库和安全审计频繁出现，说明工具链开始补齐模型与业务之间那些容易被忽略的工程层。

周报从 30 个主推荐中留下 10 个项目。它们既有官方 SDK 和完整平台，也有体量不大但问题定义清楚的工具；放在一起看，更像一张 Agent 系统从开发、运行到治理的路线图。

## 一、Agent 的运行入口与控制面

### 1. Chrome DevTools MCP：让 Agent 直接读取浏览器事实

[Chrome DevTools MCP](https://github.com/ChromeDevTools/chrome-devtools-mcp) 是官方 Chrome DevTools MCP server，可让编码 Agent 读取 console、network、截图、性能 trace 和 heap snapshot，也能操作真实浏览器页面。

**适合：** 前端调试、视觉验证和性能排查中经常需要 Agent 获取页面真实状态的开发者。

**注意：** MCP client 能接触浏览器内容，应使用非敏感 profile；usage statistics、CrUX 查询和更新检查也要按团队环境决定是否关闭。

### 2. openai-agents-python：轻量但完整的官方 Python Agent SDK

[openai-agents-python](https://github.com/openai/openai-agents-python) 覆盖工具调用、handoff、guardrails、tracing、session 和 realtime 工作流，API 相对简洁，文档与示例也给出了从原型到生产的明确路径。

**适合：** 使用 Python 和 OpenAI API，希望快速搭建可追踪 Agent 服务的团队。

**注意：** 深度采用会涉及 API 费用和数据边界，第三方 provider 兼容性也需要逐项验证。生产前应锁版本，并先在低风险内部工具中跑通 guardrails 与 tracing。

### 3. nanobot：把个人 Agent 需要的组件放进一个轻量运行时

[nanobot](https://github.com/HKUDS/nanobot) 提供 WebUI、聊天渠道、工具、记忆、MCP、模型路由和自动化，已经形成个人或小团队 Agent 工作台的完整运行面。

**适合：** 想自托管个人助手，或比较不同 provider、memory 和聊天入口的人。

**注意：** 项目增长很快，Issue 和 PR 也很多。部署 WebUI 与聊天渠道时要限制公网访问、token、文件和 shell 权限，先从只读工具集开始。

### 4. nexent：面向团队的 Agent 生成与运营平台

[nexent](https://github.com/ModelEngine-Group/nexent) 围绕工具、技能、记忆、编排和控制面构建零代码 Agent 平台，提供 Docker、Kubernetes 和 Helm 部署材料，更接近企业内部的 Agent 工厂。

**适合：** 需要私有知识助手、权限治理和统一运营入口的团队。

**注意：** 功能面宽意味着部署与运维成本高，默认分支也不是稳定发布分支。试用时应先验证 RBAC、租户隔离、知识库权限、quota 和升级路径。

## 二、观测与成本不能等上线后再补

### 5. HyperDX：统一查看日志、指标、链路和会话回放

[HyperDX](https://github.com/hyperdxio/hyperdx) 基于 ClickHouse 和 OpenTelemetry，将 logs、metrics、traces、errors 与 session replay 放进同一排障界面。它不是 Agent 专用工具，却能解决 Agent 服务上线后最现实的可观测问题。

**适合：** 已经有小规模 AI 服务，希望统一排查模型调用、工具执行和用户会话的团队。

**注意：** ClickHouse、collector、数据保留和 session replay 都会带来部署与隐私成本。建议先接一个非生产服务，并明确 PII 脱敏和 retention 策略。

### 6. TokenTracker：本地追踪 AI coding 的 token 与费用

[TokenTracker](https://github.com/mm7894215/TokenTracker) 覆盖多种 coding CLI 和桌面工具，通过 CLI、dashboard 和 widgets 展示项目、模型与用量归因，适合把模糊的“最近花得有点多”变成可检查的数据。

**适合：** 同时使用 Codex、Claude Code、Cursor 或 Gemini CLI 的个人和小团队。

**注意：** 解析依赖各工具日志格式，上游变动可能影响准确性。团队场景可以先只启用 CLI 与 dashboard，核对归因后再考虑桌面组件。

## 三、沙箱、知识与安全边界

### 7. sandboxd：给 coding agent 一个可运行、可回滚的应用环境

[sandboxd](https://github.com/tastyeffectco/sandboxd) 让编码 Agent 在隔离容器内构建真实应用，并提供预览 URL、diff、snapshot、fork 和 restore。它把 Agent 产物从代码片段推进到可以打开和验证的环境。

**适合：** 正在评估 AI app builder，或需要为 Agent 提供临时运行环境的团队。

**注意：** 容器不是虚拟机，多租户不可信代码需要 gVisor 或更强隔离；凭据代理、预览 URL、secrets 和网络出口也必须单独审计。

### 8. reflect-open：Agent 友好的本地 Markdown 知识产品

[reflect-open](https://github.com/team-reflect/reflect-open) 是本地优先的 Markdown 笔记应用，包含桌面与移动相关代码、插件、设计系统和本地文件工作流。它介于普通编辑器和长期记忆服务之间，更像一个可被 Agent 读写的完整知识产品。

**适合：** 希望保留本地 Markdown，同时尝试日历笔记、联系人笔记和 AI prompt 工作流的用户。

**注意：** beta 与 Release 节奏较快，移动端、本地文件和同步策略仍可能变化。先用复制出来的 vault 测试迁移和备份，不要直接接入唯一知识库。

### 9. VulnHunter：从漏洞发现走到修复和验证

[VulnHunter](https://github.com/capitalone/VulnHunter) 将攻击者视角的源码分析拆成 hunt、fix、verify 和 benchmark runtime 工作流，提供 Claude Code 与 AWS Bedrock 等接入方式，是安全 Agent 闭环的早期样本。

**适合：** 想评估 Agent 辅助代码审计，并能提供授权测试仓库的安全团队。

**注意：** 这是双用途能力，只能用于授权代码库和隔离环境。项目历史还短，真实检出率与误报率必须通过已有漏洞样本和人工结论对照。

### 10. Microsoft Agent Framework：覆盖 Python 与 .NET 的企业工作流

[Microsoft Agent Framework](https://github.com/microsoft/agent-framework) 提供顺序、并发、handoff 和群组工作流，并把 checkpoint、streaming、人工介入与 OpenTelemetry 放进 Python 和 .NET 技术栈。

**适合：** 希望用 Python 或 .NET 构建可持久化、可人工审批 Agent 流程的团队。

**注意：** 深度接入 Azure Foundry 会带来供应商绑定、凭据、费用和数据边界问题；建议先固定版本，在本地验证完整工作流。

## 本周优先试用

如果只选一个：

- 前端开发可以先接入 **Chrome DevTools MCP**；
- 已有 AI 服务可以用 **HyperDX** 补一条观测链路；
- 想验证 Agent 生成应用，可以在一次性环境中试 **sandboxd**。

完整周报记录了版本、维护证据、许可证和各项目更具体的试用边界。
