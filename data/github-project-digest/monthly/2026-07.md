## 真实业务与项目机会

### 1. 跨工具 AI 编程用量与成本台账

- 形态：企业内部工具
- 目标用户：同时试用两种以上 AI 编程工具的平台工程或研发效能负责人
- 需求状态：有需求信号
- 竞品数量：4
- 组合仓库数量：2
- 最高验证等级：L2
- 组合结论：部分可行
- 商业判断：值得做技术实验
- 核实日期：2026-07-20

#### 真实问题

GitHub 和 Google 都为各自 AI 编程产品提供组织级采用、活跃用户和用量指标，说明研发管理者确实需要监控这类数据；但两套指标受各自产品 surface 限制。跨工具统一口径仍是由官方能力边界推导出的缺口，尚无付费访谈，因此只标“有需求信号”。

#### 市场与现有方案

| 方案 | 类型 | 部署/流程 | 公开价格 | 已核实限制 |
|---|---|---|---|---|
| GitHub Copilot usage metrics | 商业产品 | GitHub 托管 dashboard、API、NDJSON | 指标功能单独价格未知 | 只覆盖 Copilot 定义的 surfaces；团队指标需 join 报告 |
| Gemini Code Assist monitoring | 商业产品 | Cloud Monitoring、日志与自定义指标 | 指标功能单独价格未知 | 主要覆盖 Gemini；部分指标仅 IDE 交互 |
| OpenLIT | 开源/自托管 | OTel SDK/Collector、ClickHouse 和 dashboard | 部署成本未知 | 面向应用运行时 LLM 可观测性，不直接解析本地编码代理会话 |
| 厂商导出 + 表格/自建 BI | 现实流程 | 下载 NDJSON/监控数据后人工 join | 人力成本未知 | 口径、身份、刷新和权限由团队维护 |

#### 产品定义

第一版是内部聚合台账：参与者本地生成聚合 JSON，适配器只保留日期、provider、model、token、估算成本与 session 计数，再导入单文件分析库。它不读取或上传提示词/代码，不做个人排行榜，也不把 token 数解释成生产率。

#### 仓库组合

##### 1. CodeBurn

- 仓库：[getagentseal/codeburn](https://github.com/getagentseal/codeburn)
- 来源身份：本月核心
- 职责：解析多种本地编码工具会话并输出聚合 JSON
- 接入方式：`status/report/export --format json` → 隐私适配器
- 验证等级：L2

##### 2. DuckDB

- 仓库：[duckdb/duckdb](https://github.com/duckdb/duckdb)
- 来源身份：补充组件
- 职责：单文件分析存储和 SQL 聚合
- 接入方式：适配后的 JSON → `read_json`/`COPY` → 汇总查询
- 验证等级：L0

#### 组合链路

`本地编码工具会话 → CodeBurn 聚合 → JSON 隐私适配器 → DuckDB → 固定 SQL 汇总 → 负责人复核`。CodeBurn 与 DuckDB 职责不重叠，但没有官方直连适配器；L3 因 DuckDB Node 包下载受阻而未完成，所以结论是“部分可行”。

#### 自行开发部分

需要 schema allowlist、幂等导入、身份哈希、保留与删除、provider/model/currency 映射、SSO/权限和审计。CodeBurn 团队 sync 仍是 preview，不作为首版已验证基础设施。

#### MVP 验证

选择一支 10–30 人且明确同意的双工具试点团队，连续 14 天导入不含提示词/代码的聚合 JSON。成功标准是负责人能对齐至少两种工具的日期、模型和成本口径，并回答一项原厂 dashboard 无法回答的跨工具问题。若必须上传原始会话、参与者不同意边界、两周内无法稳定映射两种工具，或维护成本高于直接用厂商导出，则停止。

#### 业务判断

该方向最可能帮助已有多工具试点的平台工程团队统一最小口径；最大阻力是员工监控观感、数据敏感性、成本估算误差和 schema 变化。在用户访谈与真实团队 L4 前，只值得做技术实验，不进入商业开发。

#### 证据边界

已证实：两家厂商提供组织指标；CodeBurn 可输出多工具聚合 JSON；DuckDB 文档支持 JSON 导入。推断：多工具团队需要统一台账。未验证：真实团队采用意愿、跨设备身份映射、L3 数据连接、效率改善、收入、客户数与市场规模。
