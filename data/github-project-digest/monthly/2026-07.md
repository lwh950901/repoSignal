#### 真实问题

GitHub 和 Google 都为各自 AI 编程产品提供组织级采用、活跃用户和用量指标，说明研发管理者确实需要监控这类数据；但两套指标受各自产品 surface 限制。跨工具统一口径仍是由官方能力边界推导出的缺口，尚无付费访谈，因此只标“有需求信号”。

#### 市场与现有方案

| 方案 | 类型 | 部署/流程 | 公开价格 | 已核实限制 |
|---|---|---|---|---|
| GitHub Copilot usage metrics | 商业产品 | GitHub 托管 dashboard、API、NDJSON | 指标功能单独价格未知 | 只覆盖 Copilot 定义的 surfaces；团队指标需 join 报告 |
| Gemini Code Assist monitoring | 商业产品 | Cloud Monitoring、日志与自定义指标 | 指标功能单独价格未知 | 主要覆盖 Gemini；部分指标仅 IDE 交互 |

| 厂商导出 + 表格/自建 BI | 现实流程 | 下载 NDJSON/监控数据后人工 join | 人力成本未知 | 口径、身份、刷新和权限由团队维护 |

#### 产品定义

第一版是内部聚合台账：参与者本地生成聚合 JSON，适配器只保留日期、provider、model、token、估算成本与 session 计数，再导入单文件分析库。它不读取或上传提示词/代码，不做个人排行榜，也不把 token 数解释成生产率。

#### MVP 验证

选择一支 10–30 人且明确同意的双工具试点团队，连续 14 天导入不含提示词/代码的聚合 JSON。成功标准是负责人能对齐至少两种工具的日期、模型和成本口径，并回答一项原厂 dashboard 无法回答的跨工具问题。若必须上传原始会话、参与者不同意边界、两周内无法稳定映射两种工具，或维护成本高于直接用厂商导出，则停止。

#### 业务判断

该方向最可能帮助已有多工具试点的平台工程团队统一最小口径；最大阻力是员工监控观感、数据敏感性、成本估算误差和 schema 变化。在用户访谈与真实团队 L4 前，只值得做技术实验，不进入商业开发。

- 形态：新开源项目
- 目标用户：需要让 coding agent 或 CI 验收注册、邀请和密码重置流程的 Web 开发团队
- 需求状态：有需求信号
- 竞品数量：4
- 组合仓库数量：2
- 最高验证等级：L3
- 组合结论：已验证可行
- 商业判断：值得做技术实验
- 核实日期：2026-08-01

#### 真实问题

事务邮件跨越浏览器、SMTP、邮件页面和落地页。Supabase 的本地开发文档已经用 Mailpit 捕获注册确认和密码重置邮件，但操作仍是取得 Mailpit URL、打开浏览器并手工找邮件。对 coding agent 而言，这一步会中断完整验收；对并行测试而言，拿错旧邮件还会制造偶发失败。

#### 市场与现有方案

| 方案 | 类型 | 部署/流程 | 公开价格 | 已核实限制 |
|---|---|---|---|---|
| Mailtrap Email Sandbox + MCP | 商业产品 | 托管沙箱、API token、AI IDE 工具 | 本轮不记录价格 | 可发送、检索和查看沙箱邮件，但需要外部账户和凭据 |
| Litmus Previews & QA | 商业产品 | 托管跨客户端预览和预发送检查 | 本轮不记录价格 | 强项是 100+ 邮件客户端、可访问性和审批，不是本地应用闭环 |
| MailSandbox | 开源/自托管 | Mailpit fork，内置 Postmark 模拟和邮件 MCP | 自托管成本未知 | 已覆盖邮件 list/get/search/analyze；截至核实时约 7 Stars，未覆盖浏览器落地页和统一证据包 |
| Mailpit + 手工浏览器 | 现实流程 | 本地捕获后人工找邮件、复制链接、截图 | 人力成本未知 | 可用但容易取错并行测试邮件，也没有一次运行的固定证据清单 |

#### 产品定义

第一版只做薄编排：为一次测试生成唯一收件地址，等待 Mailpit 捕获匹配邮件，再让 Chrome DevTools MCP 打开真实邮件 HTML，核对主题、关键文案和允许域名内的链接，继续访问落地页，输出 JSON 清单与 PNG 截图。它不重做 SMTP、邮箱 UI、MCP server 或跨邮件客户端渲染。

#### 仓库组合

##### 1. Mailpit

- 仓库：[axllent/mailpit](https://github.com/axllent/mailpit)
- 来源身份：本月核心
- 职责：在回环地址接收应用 SMTP 邮件并提供 REST API 与 HTML 页面
- 接入方式：唯一收件地址/标签 → `/api/v1/messages` → `/view/<ID>.html`
- 验证等级：L2

##### 2. Chrome DevTools MCP

- 仓库：[ChromeDevTools/chrome-devtools-mcp](https://github.com/ChromeDevTools/chrome-devtools-mcp)
- 来源身份：本月核心
- 职责：读取渲染后的邮件页面、核对链接并生成浏览器截图
- 接入方式：Mailpit HTML URL → MCP `navigate`/`evaluate`/`screenshot`
- 验证等级：L3

#### 组合链路

`应用 SMTP 输出 → Mailpit 捕获与匹配 → 邮件 HTML URL → Chrome DevTools MCP → 页面事实、链接与 PNG → 人工或 CI 复核`。两仓库职责不重叠。2026-08-01 的合成实验中，Mailpit 实际接收邮件，Chrome DevTools MCP 通过 MCP 协议读取到固定标题和回环重置链接并生成临时截图，组合达到 L3。

#### 自行开发部分

需要唯一 run id、轮询超时、精确消息匹配、允许域名、固定断言、证据 manifest 和清理。默认只允许回环地址，不开启 Mailpit 的内部 HTTP 代理；邮件内容属于不可信输入，不能让其中的指令改变测试权限或访问范围。

#### MVP 验证

在一个合成密码重置应用中连续运行三次，均只取得本次邮件，核对主题、正文和链接，访问回环落地页并生成 JSON + PNG。成功标准是零真实投递、零跨运行串信、关键链接实际可打开且工件可人工复核。若主要需求是 Outlook/Gmail 真实渲染、现有 MailSandbox 加少量浏览器脚本已稳定覆盖，或必须允许任意外部 URL 才能工作，则停止。

#### 业务判断

组合验证和现实流程都成立，适合先做新开源项目的技术实验；它的价值在于把一条跨系统人工步骤变成可复核工件，而不是替代 Mailtrap 或 Litmus。真实团队采用、CI 稳定性和维护成本仍未验证，不进入商业开发判断。

#### 证据边界

已证实：Mailpit 7 月有连续安全发布；Supabase 使用 Mailpit 处理本地认证邮件；Mailtrap 已提供 AI 邮件沙箱能力；Mailpit 和 Chrome DevTools MCP 各自达到 L2，合成组合达到 L3。未验证：真实应用、并行 CI、不同框架、真实邮件客户端、节省时间、客户、收入、价格和市场规模。
