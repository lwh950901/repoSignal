## 真实业务与项目机会
### 1. 可溯源的本地知识助手

- 形态：新开源项目
- 目标用户：重视数据留在本机的个人与小型团队；需要从自己的笔记和资料中查到答案并逐条核对出处。
- 需求状态：有需求信号
- 竞品数量：3
- 组合仓库数量：3
- 最高验证等级：L2
- 组合结论：文档层面可行
- 商业判断：值得做技术实验
- 核实日期：2026-10-01

#### 真实问题

用户把笔记、文件和会话分散保存，查资料时仍要手工搜索、复制和核对原文。问题频率与耗时尚无访谈测量。两类独立需求信号是 SiYuan 用户对同步丢失与恢复的具体问题，以及 LangChain 用户对答案内联引用的请求；它们分别支持数据所有权和可核对出处的需求，但不能证明同一批用户要购买完整组合。已确认的是这些具体工作流，付费意愿和目标人群规模为待验证假设。

#### 市场与现有方案

| 方案 | 类型 | 部署/流程 | 公开价格 | 已核实限制 |
|---|---|---|---|---|
| SiYuan | 开源/自托管 | 本机工作空间、可选同步 | 具体套餐未知 | AGPL-3.0；同步恢复和 Agent 写权限需单独测试 |
| Obsidian | 商业产品 | 本地笔记与插件 | 当前价格未核 | 引用校验和本方案组合边界未实测 |
| 文件夹 + 搜索 + 人工核对 | 现实人工流程 | 手动搜索、复制原文、逐条标注来源 | 人力成本未知 | 不能自动保留可重放的检索证据 |

原市场机会“客户问题：资料散落各处，答案没有出处可查；预期结果：每条结论都能指回来源”保留；具体购买需求仍是假设。现有 SiYuan 已覆盖本地笔记，因此唯一值得检验的缺口是可导出的逐条证据包，而不是再做一个笔记编辑器。

#### 产品定义

原始定位是把 Utopia 的离线时态知识底座、SiYuan 的本地知识工作空间和 Sibyl Memory 的 SQLite/FTS5 长期记忆先拼成可试用组合。原始差异化是全部组件来自当日新发现，先试用再判断；月度收窄为“本地资料→带引用检索→人工核对”的只读层。若现有 SiYuan 搜索足够，产品缺口即不成立。

##### 为什么现在可行

原始依据是三项组件来自同一批本地、检索与 Agent 能力面，技术上有可试用入口；SiYuan 提供本地数据结构，Sibyl 提供 SQLite/FTS5 检索思路，Utopia 提供时态与出处模型。新增核验只到接口/文档，三方 schema 尚未接通，不能把“供给存在”写成可交付产品。

#### 组合链路

原始验证路径要求先分别试用三项，再打通最小数据流；旧版同时要求固定版本、隔离环境和自有数据复测。计划链路为 `SiYuan 只读导出 → 自研块 ID 映射 → Sibyl FTS5 检索 → Utopia 时态/出处核对 → 人工验收`。SiYuan 上游发布和本地工作空间流程提供单仓库 L2 参考，本机未复跑；其余为文档可行，块 ID 与时态 schema 未确认，L3 未跑通。

#### 自行开发部分

需要只读导入器、块 ID/版本映射、引用校验、删除与恢复、离线网络检查和可导出证据包。第一版不做编辑器、云同步、自动写回、推断事实或多 Agent 协作。

#### MVP 验证

保留原范围“分别试用各组件并记录产出，再打通 Utopia、SiYuan、Sibyl 的最小数据流”。用 20 份自有脱敏笔记和 20 个已知答案问题，周期 14 天。成功指标：引用可人工核对率 ≥90%，导出/重导入无丢失，未授权外联 0 次。失败指标：两轮内无法保留来源 ID，或引用错配超过 10%。停止条件：14 天仍无法完成只读导入—检索—回查，或目标用户用现有搜索即可完成任务。

#### 业务判断

原始可行性评分：81/100（中），是日常组合评分，不替代月度验证结论。问题真实性有独立信号但频率未知；单仓库最高 L2、组合仅文档可行；最大不确定性是用户是否需要第二套索引。值得做技术实验；下一步唯一动作是用授权脱敏笔记做一次只读来源 ID 回查实验。

#### 证据边界

原始风险逐条保留：Utopia 的“企业世界模型”效果是项目方自述，错误本体会放大错误推导；SiYuan 的 AGPL-3.0、同步商业边界和 Agent 批量改笔记风险；Sibyl 社区与采用规模小、公开基准未复测、激活可能写入凭据并连接账户服务，Windows 仅支持 WSL2。新增边界：无用户访谈、无独立付费证据、无实测三方格式映射；本机 L3 受环境限制。SiYuan 的上游流程不代表本机组合已验证。

#### 真实问题

员工跨部门查资料，手工检索后需要核对原件；涉及写入动作时须交审批。频率和损失尚无真实企业样本。两类独立需求证据是 LangChain 用户要求答案内联引用，以及 GitHub 文档对受保护分支状态检查和人工审查的正式约束。前者证明引用需求，后者证明审批流程存在；“同一企业要购买一体化助手”仍是待验证假设。

#### 市场与现有方案

| 方案 | 类型 | 部署/流程 | 公开价格 | 已核实限制 |
|---|---|---|---|---|
| Microsoft 365 Copilot Search | 商业产品 | 托管企业搜索，依已有访问权限返回资料 | 当前套餐价格未核 | 依赖 Microsoft 365 权限与连接器；本方案审批链未对照实测 |
| Cognee / Coze Loop | 开源自托管替代 | 本地检索与评测追踪 | 自托管成本未知 | 仍需自己处理身份、引用、评测与数据保留 |
| 文件检索 + 工单审批 | 现实人工流程 | 人工找原件、复制引用、等待批准 | 人力成本未知 | 证据在文档与工单间分散 |

原市场机会“数据敏感企业是否愿意为‘数据不出境 + 答案可追溯’付费”保留为待验证假设；原方案也确认近 90 天编排、检索、记忆、沙箱、评测组件均有候选，这仅是供给事实。产品缺口是同一授权样本上的引用核验和审批证据，而非泛化“企业一定需要新的 RAG”。

#### 产品定义

保留原定位：部门文档进入私有知识库，回答须有出处，动作须经人工批准。原差异化是把数据私有化、审批和评测一并交付。第一版限定一个部门、一组权限、一项模拟动作；不承诺真实合规认证。

##### 为什么现在可行

原组合依据是编排、检索、记忆、沙箱和评测都有候选，能设计“问答＋审批执行”自托管闭环。月度新增的 LangChain 检索接口、Cognee 数据层和 Coze Loop 评测接口支持分工；真实身份、引用 schema 与执行隔离仍未连接。

- 接入方式：输入：脱敏问答与引用结果；输出：trace 和评测报告；接入：本地 SDK/HTTP，禁止原始敏感文本默认上报。
- 验证等级：L0

#### 组合链路

原验证路径是固定版本、隔离环境、自有数据复测。设计链路为 `授权文档 → Cognee 检索 → LangChain 带出处问答 → 自研人工审批 → CubeSandbox 模拟动作 → Coze Loop 评测`；MARM 是二期记忆槽位。LangChain 官方检索最小流程与测试给出上游 L2 参考，本机未复跑；其余只有 L0/文档接口，身份和引用格式未确认。Docker socket 无权限，L3 未通过。

#### 自行开发部分

需要文档 ACL、引用/版本 ID、审批工单适配、执行 allowlist、评测基准、脱敏和留存规则。第一版不做跨部门全量索引、不启用 MARM 写入、不执行真实业务动作。

#### MVP 验证

保留原范围：一个部门文档集、一条评测集、一个必须审批的动作，记忆和沙箱二期。测试数据为一组授权脱敏语料、20 条已知答案、1 项模拟审批，周期 14 天。原成功指标保留：30 条上下文召回抽检准确率 ≥90%，50 条带出处答案引用可核对率 ≥90%，20 次端到端执行且失败可恢复率 100%。失败指标：核心链路两轮内不通、指标低于阈值一半、样本不可复现、许可证不合规或需闭源付费组件才能闭环。停止条件：周期结束不达标立即停；无 3 位可访谈目标用户时仅保留技术实验。

#### 业务判断

原始可行性评分：88/100（高），是日常技术组合评分；原需求证据为 59/100（低、项目方自述），不替代月度判断。问题有独立信号但行业用户尚未确认；组合只有上游单仓库 L2，最大不确定性是权限和引用链。值得做技术实验；下一步唯一动作是拿一份授权脱敏部门资料测试“检索→引用回查→模拟审批”。

#### 证据边界

原始风险逐项保留：LangChain 模块/Provider 版本及外部模型费用和数据传输；Cognee 数据隔离、Provider 成本、图/向量后端与 Release 描述；MARM 社区小、分支和 embedding/SQLite 迁移；CubeSandbox 的 Linux x86_64/KVM/PVM、网络策略和模板运维；Coze Loop 的多依赖部署、公网注册、SSRF、横向越权和 Release 滞后。新增风险是采购意愿、数据驻留、身份映射、引用误报、审批职责与商业价格未知；没有企业真实数据或 L3。

### 3. 可审计的 Agent 开发交付平台

- 形态：企业内部工具
- 目标用户：已用编码 Agent 的研发团队和平台工程组；需要让写仓库前的执行、评测、审计与批准可重放。
- 需求状态：有需求信号
- 竞品数量：3
- 组合仓库数量：5
- 最高验证等级：L2
- 组合结论：文档层面可行
- 商业判断：值得做技术实验
- 核实日期：2026-10-01

#### 真实问题

Agent 任务失败、重试或写仓库时，团队要手动找日志、比较输出、核对权限再审批。频率及损失无访谈数据。两类独立需求证据是 Trigger.dev 用户提出并发去重/重试副作用问题，以及 GitHub 的必需状态检查与人工审批机制。它们证实恢复和发布门禁的工作流存在，不证明所有团队要新平台。

#### 市场与现有方案

| 方案 | 类型 | 部署/流程 | 公开价格 | 已核实限制 |
|---|---|---|---|---|
| Trigger.dev | 商业产品与开源部署 | 托管长任务或 Docker/Kubernetes 自托管 | 当前套餐价格未核 | 重试不自动保证外部副作用幂等 |
| GitHub Actions | 商业/托管替代 | 工作流、保护分支、审批 | 当前价格未核 | 仍需自行做 Agent 轨迹、成本、沙箱与证据格式 |
| 日志 + PR 人工检查 | 现实人工流程 | 汇总命令日志、评测结果后人工审批 | 人力成本未知 | 证据分散、失败重跑口径不一致 |

原市场机会“跑挂了怎么恢复、花了多少钱、有没有越权”的紧迫度保留为待验证假设；近 90 天隔离与观测候选明显变多只是供给事实。缺口限于一次受控 Agent 任务的可重放证据包，不另造通用 CI。

#### 产品定义

原定位是“像 CI 一样让 Agent 在沙箱内执行、全程留痕、出审计报告，人工批准后才写仓库”。原差异化是比单个 harness 或观测工具多一条隔离执行—trace—评测—审批流水线。首版只做固定仓库的只读任务和模拟写入。

##### 为什么现在可行

原组合依据是长任务恢复、观测和安全执行组件齐备；9 月 promptfoo 的评测输出、sandboxd 的隔离接口、OmniRoute 的调用路由可分别核验。真正的跨仓库身份、成本和审计 schema 尚未连接。

#### 组合链路

#### 自行开发部分

需要统一任务 ID、幂等键、证据包 schema、密钥隔离、权限策略、人工签核、日志脱敏和失败回放。第一版不做自动写仓库、自动合并、多租户、不可信互联网代码执行。

#### MVP 验证

保留原场景“沙箱内执行→留痕与审计报告→人工批准后写仓库”；首版以模拟写入代替真实提交。测试数据是自有固定 commit、3 条任务步骤记录含失败例、模型调用记录及 1 个不可信输入边界清单，周期 14 天。原成功指标：扫描问题 100% 有独立验证结论，20 次端到端执行且恢复率 100%，用量记录与路由偏差 ≤10%。失败指标：两轮不通、指标低于阈值一半、抽检不可复现、组件维护停滞或须闭源组件才闭环。停止条件：14 天未达标即停；找不到 3 位可访谈用户则不进入产品开发。

#### 业务判断

原始可行性评分：81/100（中），是日常技术组合评分；原需求证据为 59/100（低、项目方自述）。恢复和审批问题有独立信号，但组合仅单仓库上游 L2、最大不确定性是事件关联和权限边界。值得做技术实验；下一步唯一动作是在自有测试仓库以模拟写入跑一条固定任务的证据包。

#### 证据边界

原始风险逐项保留：sandboxd 仍为 Beta，默认容器不是 VM；promptfoo 结果依赖样本/断言和模型成本，红队仅限授权目标；Codex Security 的受保护访问、API 权限和成本，不能替代静态扫描、依赖扫描与人工审计；OmniGENT alpha、策略/权限与运维复杂；OmniRoute 集中 Provider 凭据、路由回退可能改变能力、成本和数据地域。新增风险是需求频率未知、跨仓库 schema 未确认、Docker/npm 受阻、无 L3/真实写入；无采购或收入证据。
