## 真实业务与项目机会

### 1. 本地优先个人 AI 工作台

- 形态：新开源项目
- 目标用户：重视隐私的个人开发者、知识工作者与小型团队；他们在本机文件、笔记、多个模型账户和手工复制的会话摘要之间反复切换。
- 需求状态：有需求信号
- 竞品数量：3
- 组合仓库数量：5
- 最高验证等级：L2
- 组合结论：文档层面可行
- 商业判断：值得做技术实验
- 核实日期：2026-09-01

#### 真实问题

目标用户在做研究、写作或开发时，希望把资料与长期记忆留在本机，却还要手动在模型 Provider、个人笔记、CLI 和检索工具之间复制上下文。独立需求证据分为两类：本月已有本地 Agent 工作台和本地模型网关的可安装产品材料；而 Cognee 的本地嵌入式开发路径和 Google ADK 的工作流/样例表明“记忆、检索、编排”确实被分别交付。已确认的是这些分散流程和可替代产品存在；“个人愿意为数据不离开本机付费”只来自原方案，仍是待验证假设。

#### 市场与现有方案

| 方案 | 类型 | 部署/流程 | 公开价格 | 已核实限制 |
|---|---|---|---|---|
| OpenWorker | 商业化路径/开源桌面替代 | 本机桌面应用、连接器、MCP 与执行前确认 | 未知 | Open beta，OAuth、桌面文件权限与自动更新须隔离核验 |
| Cognee | 开源/自托管替代 | Python/容器或本地嵌入式记忆与图/向量检索 | 开源部署成本未知 | LLM key、后端选择和生产图存储仍需治理 |
| 本地笔记 + 多个模型客户端 | 现实人工流程 | 手动复制资料、摘要与模型输出 | 人力成本未知 | 没有统一会话、数据格式、回滚与检索边界 |

原始市场机会“池里本地优先、自托管类项目反复出现，个人为数据不离开本机付费的趋势在上升”保留为待验证假设；它不能替代访谈或付费证据。用户不能直接只用上述任一产品的缺口是：首版限定为可导出的本地会话/记忆格式、允许 Provider 选择、并在写入前给出可复核的数据边界，而不是再做一个通用聊天壳。

#### 产品定义

原始业务定位保持为“数据全部留在本机、模型可自由切换、记忆可导出的个人 AI 工作台”。第一版只编排本地文本/元数据：导入一份用户明确授权的 Markdown 笔记，写入可导出的记忆层，由一个受限 Agent 读取后生成摘要；不接 OAuth、不抓取网页、不上传提示词，也不承诺免费 Provider 可用性。

##### 为什么现在可行

原始可行性依据是“本地记忆、模型网关、Agent 编排在池里都能找到”；8 月的 ADK Go、ADK Python、FreeLLMAPI 和历史 Cognee/MARM 让组件职责可以分开核验。但现阶段只证明接口和部署材料存在，不证明完整产品体验已经可用。

#### 组合链路

原始验证路径是“固定版本、隔离环境、自有数据复测”。目标链路为 `授权 Markdown → 记忆适配器 → Cognee/MARM 本地检索 → ADK Go 固定任务 → FreeLLMAPI loopback → 摘要与导出文件`。ADK Go 的官方最小样例/发布检查是已复核的 L2 依据；本机没有 Go 工具链且未配置模型凭据，未复跑。Docker socket 不可用、Cognee 需要 LLM key，因此没有把任何 L3 连接写成跑通。

#### 自行开发部分

需要本地 schema、导出/删除、加密或操作系统权限、Provider allowlist、模型响应脱敏、版本迁移、失败回滚和可读审计日志。第一版不做桌面壳、OAuth、跨设备同步、自动抓取、团队空间和多 Agent fleet。

#### MVP 验证

保留原始 MVP 范围“本地记忆写入 → Agent 读取 → 输出压缩”，只用 20 份脱敏 Markdown 和一个固定摘要问题，周期 5 个工作日。成功指标是同一资料能稳定导出、重新导入并被固定任务召回，且没有网络请求或未授权文件读取。失败指标是必须上传原文、Provider 依赖导致流程不可重复，或检索结果无法由人工追溯。停止条件是五天内不能完成一次本地导入—检索—导出闭环，或用户明确只需要现有笔记/模型客户端。

#### 业务判断

原始可行性评分：83/100（中），它是日常组件组合评分，不替代本月验证结论。问题真实性为有需求信号，组合目前只有单仓库 L2/文档可行，最大不确定性是本地数据边界是否值得用户为额外配置成本买单。值得做技术实验；下一步唯一动作是在一名授权用户的脱敏资料上执行一次离线导入—检索—导出测试。

#### 证据边界

#### 真实问题

当前工作流是真实存在的：GitHub 允许受保护分支要求 PR 审查、状态检查和部署成功，说明变更并不能直接合并；Agent 产生修复时仍要由人复核。另一类独立证据是 AI-Infra-Guard 将 Skill、MCP、Agent 与 AI 基础设施扫描分为独立入口，证明安全扫描面实际存在。已确认的是发布前审批/检查和扫描工具的存在；“企业会购买完整 Agent 安全平台”是原方案的待验证假设。

#### 市场与现有方案

| 方案 | 类型 | 部署/流程 | 公开价格 | 已核实限制 |
|---|---|---|---|---|
| GitHub Code Security / branch protection | 商业产品/托管流程 | PR、必需 review 与 status check | 具体组合价格未知 | 覆盖 GitHub 工作流，不替代 Agent/Skill/MCP 的本地扫描和证据归档 |
| AI-Infra-Guard | 开源/自托管替代 | Docker 服务或独立扫描 CLI | 自托管成本未知 | README 明确默认部署缺少认证，不能公开暴露 |
| 扫描结果 + 人工 PR 审核 | 现实人工流程 | 扫描器输出贴入工单/PR，再由安全人员判断 | 人力成本未知 | 缺少同一 run 的可重放证据链，误报/漏报仍靠人工兜底 |

原始市场机会“Agent 带来新的攻击面，安全类项目在密集出现”保留为待验证假设；不把项目热度当作客户需求。值得验证的缺口只是“将一次授权靶场扫描、受限修复建议、独立复查与人工门禁写成固定证据包”，而不是取代既有 SAST 或宣称自动放行。

#### 产品定义

原始业务定位保持为“让安全扫描由 Agent 自动跑：扫出问题、给出修复建议、独立验证是否修好，每一步留证据，由人审批放行”。首版只能在授权靶场处理一个故意设置的低风险配置问题；Agent 不能直接写受保护分支，最终动作始终是生成 PR/报告供人审阅。

##### 为什么现在可行

本期先以 Asia/Shanghai 的 2026-08-01 至 2026-08-31 为范围，合并候选账本、日报和与本月相交的周报。离线生成器确定性得到 156 个合格候选；Top 5 从其中和原始事实材料独立进行统一六维评分，不因是否进入业务组合调整。可行性目录有 8 个日期文件、22 条原始方案，按规范化标题、业务定位和核心组合去重为 7 项；阶段 A 选出本地优先工作台、安全 Agent 平台与私有知识助手，未用重复标题或改造方案凑数。阶段 B 逐项保留原始评分、定位、目标客户、市场机会、可行性依据、组合入选理由、差异化、MVP、风险和验证路径，并补入需求/替代/数据流证据。2026-09-01 的 L3 尝试被 Docker socket 权限和 Python TLS 证书链阻断；没有关闭 TLS、切换镜像、添加依赖或读取真实业务数据。所有公开判断据此冻结；构建过程不访问外部网络。
