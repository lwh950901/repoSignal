# 开源雷达周刊


这一周的 10 个项目，集中在两件事：先把 Agent 与 RAG 做成可部署、可恢复的系统，再把编码 Agent 的规格、执行与协作放进更清晰的边界里。既有可以直接搭建 PoC 的 RAGFlow、Langflow，也有更适合拆解工程方法的 Spec Kit、OpenSpec 和 code-graph-rag。

另一个明显方向是“执行”本身正在成为基础设施问题。OpenSandbox 讨论隔离，Conductor 处理持久化工作流，Paperclip 和 prime-agent 分别从团队控制面与长任务运行时切入；试用时，权限、凭据和升级路径比跑通演示更值得先确认。

## 一、从检索原型到受控执行
### 1. RAGFlow：自托管的文档检索与上下文层
RAGFlow 是面向文档和 Agent 应用的自托管 RAG 引擎，覆盖文档解析、知识库、检索、引用与上下文服务，并以多服务和 Docker Compose 方式交付。

**介绍：** 它把文档问答中常见的切分、召回和引用环节放进一套可部署的基础设施，适合用来搭一个受控的检索 PoC。

**推荐依据：** 本周周报确认其 README、Docker 启动、测试与部署路径较完整，且近期仍有 Release；日报还给出了开发态启动与代码执行器边界的材料。

**适合：** 需要自托管文档检索、知识库问答或为 Agent 提供上下文服务的团队。

**注意：** Elasticsearch 或 Infinity、MySQL、Redis、MinIO 等依赖会带来资源和运维成本；文档数据、LLM 凭据与代码执行器需要单独隔离，ARM64 镜像和第三方依赖也要先核对。

### 2. Langflow：把 Agent 与 RAG 流程先画出来
Langflow 是可视化 AI 应用工作流平台，可通过组件与代码扩展构建、调试和部署 Agent、RAG 流程，并提供 Web UI、Python 包、REST API 和 Docker 路径。

**介绍：** 它适合将模型、工具与检索组件连成可运行原型，再把可复用部分迁移到自己的代码和部署流程。

**推荐依据：** 周报与日报均给出安装、Docker、测试和部署入口，并确认仓库包含组件画布、源码开发路径以及持续维护信号。

**适合：** 希望快速验证 RAG 或 Agent 工作流、同时保留 API 与代码扩展空间的 AI 应用开发者。

**注意：** 组件和第三方依赖面较广；流程能跑通并不等于密钥隔离、数据治理、权限控制和升级兼容性已经满足生产要求。

### 3. OpenSandbox：为 Agent 执行划出隔离边界
OpenSandbox 是面向 Agent 与自动化任务的沙箱基础设施，提供生命周期 API、MCP Server、多语言 SDK，以及 Docker 和 Kubernetes 运行路径。

**介绍：** 它把“让 Agent 执行任务”和“为执行设置隔离策略”拆成可自托管服务，便于把运行时边界单独拿出来验证。

**推荐依据：** 本周日报覆盖了生命周期、执行 API、MCP、SDK 和运行时文档；周报确认安装、示例、Docker、测试与部署信号齐全，并有持续更新。

**适合：** 正在为 Agent 产品评估执行隔离、生命周期管理或 MCP 工具承载方式的平台团队。

**注意：** 容器能启动不代表安全隔离已被证明；宿主内核、网络出口、文件挂载、凭据与资源限制都需要部署方自行做权限和故障测试。

## 二、让长任务能恢复、能审查
### 4. Paperclip：面向 Agent 团队的执行控制面
Paperclip 是开源的 Agent 团队工作管理与执行控制面，将任务、目标、心跳、预算、审批和多租户治理组织为自托管应用。

**介绍：** 它关注的不是单次模型调用，而是持续任务如何保留状态、接受审批、处理回滚，并让团队看见执行过程。

**推荐依据：** 日报记录了持久状态、原子执行、预算、审批、回滚、Secret scrubbing、tests 和 evals；周报同时确认其 Docker、测试和部署材料。

**适合：** 需要研究 Agent 团队治理、预算控制和可审计持续工作流的产品或平台工程师。

**注意：** 项目复杂度高，且开放 Issue 规模较大；多租户隔离、Agent 凭据、审批有效性与日志脱敏都不能由社区热度替代实测。

### 5. Conductor：把 Agent 长流程放进可靠工作流模型
Conductor 是面向后端团队的事件驱动、持久化工作流引擎，处理任务失败、重试、状态恢复、人工介入和执行历史回放。

**介绍：** 它提供 Java 服务、存储适配器、API/UI 和 Docker 部署形态，可把 Agent 调用嵌进已有的后端工作流而非停留在一次性演示。

**推荐依据：** 日报给出了 durable execution、回放与恢复语义、AI/Agent 工作流和相关文档证据；周报确认安装、Docker、测试和部署路径完整。

**适合：** 已有后端可靠性体系，希望为长链路 Agent 任务增加重试、暂停、恢复与追踪能力的团队。

**注意：** 系统和依赖较重；持久化工作流不会自动解决幂等、权限、成本或模型失败策略，服务与存储版本也应先锁定验证。

### 6. prime-agent：观察长任务 Agent 的持久运行时
prime-agent 是面向编码和研究长任务的 Agent Harness，将递归语言模型、持久 IPython、子 Agent、后台会话与可恢复状态组合成可编程运行时。

**介绍：** 它适合研究一个 Agent 如何跨会话持续工作、保留快照并管理子任务，而不是把长任务理解为一次更长的聊天。

**推荐依据：** 本周日报记录 RLM、Continual Harness、daemon、心跳和回滚快照，以及近期安全与恢复修复；周报也确认了测试结构和稳定/Beta 发布线。

**适合：** 想拆解编码或研究型长任务运行机制、评估会话恢复与子 Agent 协作的开发者。

**注意：** 项目明确说明模型生成的 Python 与项目命令会以当前用户权限执行，worker/kernel 不是安全沙箱；必须使用临时环境并隔离文件、网络和凭据。

## 三、为 AI 编程保留清晰工件与协作边界
### 7. Spec Kit：把规格变成可检查的工作流工件
Spec Kit 是面向 AI 编程代理的 Spec-Driven Development 工具包，将需求、原则、计划、任务和实现组织为 CLI 工作流，并以 Markdown、YAML、TOML 工件配合宿主扩展。

**介绍：** 它更像一套可阅读、可执行的工程样本，重点在于规格、状态和门禁如何进入日常开发，而不只是提供文档模板。

**推荐依据：** 日报提供了模板解析、状态管理与安全修复的证据；周报确认其 tests、templates、workflows、extensions 和 bundles 结构，以及近期维护活动。

**适合：** 想研究规格驱动的 Agent 工程流程、或在非关键仓库试验工件化协作方式的开发者。

**注意：** 模板和模型可能把错误前提固化进工件，扩展与 Bundle 也可能改变项目行为；不能把它的默认流程直接当作组织标准，安装来源与生成结果都要人工审阅。

### 8. code-graph-rag：从 AST 到代码图谱检索
code-graph-rag 是代码库理解与编辑工具：它用 Tree-sitter 解析多语言代码，写入 Memgraph 知识图谱，再把自然语言查询转换为 Cypher，并提供 CLI、MCP Server、示例与评测目录。

**介绍：** 它把“代码 RAG”拆成 Source Code、AST、Graph、Cypher 和响应的完整链路，适合沿着每一层理解结构化检索如何进入 Agent 工具调用。

**推荐依据：** 日报记录函数检索、diff 预览、结构化替换、死代码追踪和针对符号链接任意文件读写的修复；周报确认 benchmarks、evals、examples、fixtures 与 docs 的学习材料。

**适合：** 希望研究代码图谱、静态解析与 RAG 结合方式，或需要在只读环境评估代码库检索的工程师。

**注意：** 需要运行 Memgraph 并维护多语言语法覆盖；自动生成 Cypher、结构化替换和 Agent 写文件都会扩大权限边界，评测材料也不等于生产可靠性证明。

### 9. Orca：并行 Agent 编码的本地优先工作台
Orca 是面向多种编码 Agent 的本地优先并行工作台，以隔离 worktree、桌面与移动端、远程主机和终端集成组织多条任务。

**介绍：** 它将 worktree、终端分屏、远程 SSH、差异批注和协作入口放到同一控制面，适合观察多任务编码循环如何被产品化。

**推荐依据：** 日报给出了 worktree、手机 companion、远程 SSH、差异批注及 GitHub/Linear、CLI 自动化证据；周报确认多平台构建、测试材料和连续 Release。

**适合：** 同时运行多条编码 Agent 任务，且希望研究任务隔离、审查与远程协同方式的开发者或小团队。

**注意：** 工作区、远程主机与 Agent 工具都拥有较高权限；项目迭代快且开放 Issue/PR 较多，telemetry/privacy、远程连接和升级稳定性应先在临时仓库验证。

### 10. OpenSpec：以变更工件约束 AI 编程流程
OpenSpec 是规格驱动的 AI 编程工具，将 proposal、specs、design 和 tasks 组织为可执行的变更工件，并以 CLI、文档、测试和多工具适配交付。

**介绍：** 它为自由对话之外的 AI 编程提供一条结构化入口：先明确变更，再拆出设计与任务，让后续实现保留可审阅的依据。

**推荐依据：** 日报记录了 proposal/specs/design/tasks 闭环、30+ 工具适配及 CLI、测试、文档和安全结构；周报确认安装、示例、测试与近期维护信号。

**适合：** 希望在既有 AI 编程流程中引入明确变更工件，并保留人工评审与测试闸门的团队。

**注意：** 快速版本变化可能影响工件格式和命令兼容性；宿主工具接入、telemetry 与生成内容仍需审查，规格本身不能替代代码审查、测试和安全门禁。

## 本周优先试用
如果只选三个入口：想验证检索链路，可先用 **RAGFlow** 导入一小组无敏感文档；想测试执行隔离，可在独立节点试跑 **OpenSandbox** 的最小 MCP 调用；想调整 AI 编程协作，可在非关键仓库完成一次 **OpenSpec** 的 propose 流程。三者都应从固定版本、最小权限和可回收环境开始。

完整的项目依据、维护材料与上手建议见 2026-W33 完整周报。
